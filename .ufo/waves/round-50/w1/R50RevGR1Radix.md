Traces (confirm each leg of the Statement):

- `100M`: `_parse_integer_fixup_radix` base 0 → `s[0]=='1'` → base 10 (kstrtox.c:36-37 in extent).
  `_parse_integer_limit` consumes `100` (kstrtox.c:66-75 loop: `val >= base` breaks). memparse switch:
  `case 'M'` falls through `case 'K'` → `shl=20` (cmdline.c:168-175); `shl && ptr != endptr` →
  `ret <<= 20` = 104857600, `endptr++` (cmdline.c:189-194). Store: `skip_spaces` consumes `\n`,
  `*endptr == 0` → accept (sysfs.c:2040-2044).
- `010`: `s[0]=='0'`, `_tolower(s[1])!='x'` → `*base = 8` (kstrtox.c:29-33); `8 >= 8` breaks the
  digit loop at `0` — `010` → `((0)*8+1)*8+0` = 8.
- `0x10`: `isxdigit(s[2]='1')` → base 16, `s += 2` (kstrtox.c:30,38-39; `prefix_chars` handled in
  simple_strntoull vsprintf.c:87) → 16. `0X10` identical (`_tolower`).
- `10MB`: memparse consumed `M` (shl=20, endptr=3); `B` is the second letter left behind —
  `skip_spaces` stops at `B`, `*endptr != 0` → `-EINVAL` (sysfs.c:2042-2044).
- `10 M`: memparse stops at the blank (no suffix leg), shl=0, endptr=2; the store's `skip_spaces`
  hops the blank onto `M` → EINVAL. The rejection is the store's, not memparse's — the row's
  parenthetical "a blank before the suffix" is correct.
- `-1`: `-` is neither `'0'` (radix fixup untouched → base 10) nor a digit nor `a-f` → zero chars
  consumed (kstrtox.c:66-68 break), endptr=0; store sees `-` → EINVAL. Same path for `+10`.
- `\n`: zero digits, ret=0, `switch('\n')` → default, shl=0 → endptr unchanged (0); store's
  `skip_spaces` eats the newline → `*endptr == 0` → accept limit 0. `0` alone and `0K` accept the
  same way (receipt rows `0`, `1K`).

## Boundary cases the code answers (all checked in the harness)

- `0x` with no hex digit (`0x\n`, `0X\n`): base 8 is picked (`isxdigit(s[2])` fails on `\n`),
  the `0` parses, `x` is trailing → **EINVAL**. Consistent with the row's "followed by a hex digit".
- Leading `+` (`+10\n`) and leading whitespace (` 100\n`, `\t100\n`): zero digits, EINVAL — the row
  names neither; worth naming because `kstrtoull`-style callers tolerate neither here either, but a
  reader could assume scanf-style whitespace skipping. It does not skip.
- `08\n` — **EINVAL**: octal base rejects `8` (`val >= base`, kstrtox.c:73), leaving `8` trailing.
  Worth naming: a triage writer could well type `08` expecting 8.
- `0x1g\n` — **ACCEPTS 1073741824** (1 GiB): after hex `1`, memparse sees `g` as the G-suffix. The
  `a-f` letters are hex digits only where base 16 consumes them; a hex number's first non-hex letter
  is parsed as a unit suffix. Name it: `0x1e` parses as 30 (e is hex), `1e` decimal parses as 1 EiB
  (`e` is the E-suffix) — the letter boundary is base-dependent.
- `1e3\n` — EINVAL: `e` consumed as E-suffix (shl=60), `3` trailing.
- Overflow — accepted, not rejected: `2^64` decimal → `ULLONG_MAX` (kstrtox.c:80-84
  `res = ULLONG_MAX`, `KSTRTOX_OVERFLOW` bit masked out of the consumed count at vsprintf.c:91);
  `0xFFFFFFFFFFFFFFFFK` → `check_shl_overflow` → `ULLONG_MAX`, suffix still consumed (cmdline.c:189-194).
  A second letter after an overflowing value still EINVALs (`0xFFFFFFFFFFFFFFFFKK` → ULLONG_MAX value,
  `K` trailing → EINVAL). Worth naming: an over-limit write silently clamps to ULLONG_MAX ≈ no
  throttle, never an error.
- Trailing whitespace of any length is accepted: `100 \n`, `100M \n`, `100\n \n` all ACCEPT —
  `skip_spaces` (sysfs.c:2042) runs after the suffix, not just after digits. The row's "skips
  whitespace" covers this; worth making explicit.
- `\n\n` accepts as 0. An **empty** write buffer is different in the real kernel:
  `kernfs_fop_write_iter` returns 0 for a zero-length write before calling the store — so a
  zero-length write is a no-op, while a bare newline clears the limit. (kernfs is not pinned; marked
  [inference] — the harness's `ACCEPT(0)` row for `""` is the harness passing a NUL'd buffer, not
  kernfs behavior.)
- `M\n`/`K\n` with no digits — EINVAL: `ptr == endptr` so the suffix is not consumed
  (cmdline.c:189 `likely(ptr != endptr)`), the letter itself trips the store. Supports the row's
  "the suffix counts only when at least one digit came before it".

## The `[inference]` mark on the host leg — sound, and tighter than it says

Mark (line 53): "this caller [inference: by ordinary file-mode checks, which the capture does not
exercise; ACLs and LSM rules are not captured] cannot write one." Assessment:

- Sound. capture.txt:8 records `mode=644 owner=root value=0`; capture.txt:1 records `uid=1000
  CapEff=0000000000000000`. For a non-owner with `CapEff == 0`, inode write permission needs the
  group or other `w` bit; 0644 has neither → EACCES on open-for-write. Honest about the unexercised
  path: capture.sh:25 only `stat`+`cat`s the file.
- Tighter than stated: the mark lists ACLs and LSM as uncaptured, but omits that **group ownership is
  also uncaptured and cannot matter** — at 0644 the group has read-only too, so the only uncaptured
  fact that could grant write is a POSIX ACL entry (or an LSM rule, unusual to *grant*), exactly the
  caveat already written. No defect; an optional strengthening.
- The claim is scoped to "this caller" correctly — a privileged daemon or `sudo` could write; nothing
  in the mark claims otherwise.
