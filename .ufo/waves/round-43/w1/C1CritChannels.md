## QUALITY 82/85/90 assessment

QUALITY 82 requires a code-outside-fixtures view that the code cannot tell from production and pre-data fixture-gated and cached-live controls (`corpus/QUALITY.md:161`). The live leg is valuable and uses actual host paths read-only (`score-bootinputs-r43.py:27-30,310-319`), but its filtered environment and temporary cwd/source path mean it is not unconditionally indistinguishable from normal production. The user-provided frozen-control summary says mount-table-gated K7 PASS is the declared open channel, not a closed channel.

QUALITY 85 requires child-created private production-path content, no host-resolvable names leading to it, and one leak arm per channel (`corpus/QUALITY.md:167`). This counter creates tmpfs inside the child namespace and populates it using stdin (`score-bootinputs-r43.py:75-104`), but mountinfo and uid_map are directly readable distinctions, and the library's `/mnt/bca-lib.sh` path is explicit. The wording of QUALITY 85 covers namespace traces and argv/environment pathways; its demanded leak arms are not satisfied merely by documenting openness.

QUALITY 90's structure explicitly permits an override-free leg whose channels are reported open, but also says the frozen controls include a watched-only variant per readable channel and each must read below target (`corpus/QUALITY.md:177`). Accordingly, naming mount-table, uid_map, and script-path as open channels is honest and compatible with the *reporting clause*, but is not by itself consistent with the whole criterion as evidence of robustness: a mount-table-gated variant that PASSes leaves its corresponding channel control unsatisfied. The user-provided evidence says K7 mount-table-gated PASS, which is a concrete defect under the required should-fail-control rule, not a reason to relabel the channel closed.

## Cheapest mount-table leg and rootless feasibility

The cheapest operational leg that closes the mount-table observation channel is to run the scored function directly on the real host paths in a normal process (the existing live leg shape, with no new mount namespace or mounts). It has genuine production mountinfo, so the code is not in a special mount-table view. It does **not** reproduce the missing/unreadable cases, and cannot replace the N leg; use it as separate coverage, as the counter already does.

There is no leg that both creates the counter's isolated tmpfs-over-production-path fixture view and makes it mount-table-indistinguishable from production merely by dropping privileges: `/proc/self/mountinfo` exposes mounts created in that namespace. This host counter explicitly relies on unprivileged user+mount namespaces for those mounts (`:13-16,75-81,292-295`). Without root, the available safe alternative is the real-host read-only live leg; it closes the *manufactured mount-table* cue, not the fixture-path semantics. A mountinfo filter/virtualized proc view would be a different intervention and is not evidenced as available or appropriate here.
