# SrcPaccache — C2/P5 source: paccache semantics and rollback-by-cache implication

Verdict: the round-24 capture's "4 remaining cache files" are not package files; they are four empty `download-*` sandbox temporary directories left by pacman's DownloadUser path, and the package cache holds zero package archives, so rollback by cache is entirely unavailable, not limited to four files.

## Findings

1. [obs] The paccache(8) manual page at https://man.archlinux.org/man/paccache.8 (opened 2026-10-22; fetched with `curl`, HTTP 200, 10249 bytes, sha256 `03df3807b6ab42ef4c53470b82c5336fb6bdc1ea2df6abf4dd6316021a7cdfe4`; the tool read failed twice with ECONNRESET, so curl was the successful open) documents the three options the claim uses. Exact quotes from the opened page:
   - OPERATIONS > `-r, --remove`: "Remove candidate packages from the cache directory."
   - OPTIONS > `-k, --keep <num>`: "Specify how many versions of each package are kept in the cache directory, default is 3."
   - OPTIONS > `-u, --uninstalled`: "Target uninstalled packages."
   - Man-page footer: 2025-12-11, Pacman-contrib 1.13.1, matching the host's installed `pacman-contrib 1.13.1-1` (`pacman -Qo /usr/bin/paccache` → "is owned by pacman-contrib 1.13.1-1"; `paccache --version` → "paccache 1.13.1").

2. [obs] What `paccache -r -k1` removes: per the quotes above, `-r` removes candidate packages and `-k1` keeps one version of each package, so `-r -k1` removes every cached package archive except the single newest version of each package. Verified in a scratch directory with four versions of a fake package: `paccache -d -k1 -v -c <tmp>` listed `demo-1.0.0-1`, `demo-1.2.0-1`, `demo-1.10.0-1` as candidates and kept `demo-2.0.0-1` (the newest). `-k2` listed `demo-1.0.0-1` and `demo-1.2.0-1`, keeping the two newest.

3. [obs] What `paccache -r -u -k0` removes: `-u` targets uninstalled packages (the installed set from `pacman -Qq` is blacklisted inside the script), and `-k0` keeps zero versions, so `-r -u -k0` removes every cached version of every package that is not currently installed. Verified in the same scratch directory: `paccache -d -k0 -v -c <tmp>` listed all four versions as candidates (kept none); with `-u` the installed names are excluded, so the candidates are exactly the uninstalled packages' archives.

4. [obs] `pacman -Scc` semantics from pacman(8) (https://man.archlinux.org/man/pacman.8, opened 2026-10-22, HTTP 200): "Use one --clean switch to only remove packages that are no longer installed; use two to remove all files from the cache." (`-Scc` = two `-c` switches.) So the 04:10 `pacman -Scc` runs remove ALL package files from the cache, including those of currently installed packages.

5. [obs] The capture's "4" is a directory-entry count, not a package-file count. `ls /var/cache/pacman/pkg | wc -l` = 4 (matches capture block `cache-file-count` in `.ufo/waves/round-24/capture/l1-2/capture.txt:235` and `l1-3/capture.txt:228`). The four entries are all directories named `download-*`: `download-vcoq00`, `download-Lsbwhh`, `download-0jh7Uc`, `download-r5r0Ix`, each mode 0700 owned by `alpm`, each empty (`sudo -n find /var/cache/pacman/pkg -type f` returns nothing; `sudo -n find /var/cache/pacman/pkg -name '*.pkg.tar*' | wc -l` = 0).

6. [obs] The `download-*` directories are pacman's sandboxed-download temporary directories, not packages. `/etc/pacman.conf:11` sets `DownloadUser = alpm` (pacman.conf(5): "Specifies the user to switch to for downloading files."). Upstream pacman v7.1.0 source `lib/libalpm/util.c` (https://gitlab.archlinux.org/pacman/pacman/-/raw/v7.1.0/lib/libalpm/util.c, opened 2026-10-22, HTTP 200, sha256 `381618b6054859ec76807956328b78b330237273bebe10022a559b243cb5bdd2`) creates the directory with `const char template[] = "download-XXXXXX";` and `mkdtemp`, owned by the download user. The four directories' mtimes match the paused-window transactions (2026-10-20 09:31, 13:23; 2026-10-21 17:55, 18:07).

7. [inf] The P5 premise as worded in the round-24 claim ("the package cache holds 4 files") is supported by the capture's `ls | wc -l` count but that count is of directory entries; the actual package archive count is 0. Rollback by package cache is therefore unavailable for every package: `pacman -U /var/cache/pacman/pkg/<pkg>.pkg.tar.zst` has no file to point at for any package, including the boot chain and `libinput 1.31.3-1` named in `.ufo/waves/round-15/build/IncidentTimeline.md:10` as the revert option.

8. [obs] The five installs logged during the pause (zcode, tizen-sdb, tizen-sdb-debug, openssl-1.0, openssl-1.0-debug, capture `l1-2/capture.txt:122-126`) were installed with `pacman -U` from local build files under `/home/vgpnk/.cache/yay/...` (capture `l1-2/capture.txt:240-` and `pacman.log` lines 3161, 3164, 3169). That `~/.cache/yay` directory no longer exists on the host (`ls /home/vgpnk/.cache/yay` → "No such file or directory"; no `yay*` under `~/.cache/`), and no `zcode-3.16.2-1-x86_64.pkg.tar.zst` or `openssl-1.0-1.0.2.u-7-x86_64.pkg.tar.zst` exists anywhere on the filesystem (`find / -xdev -name 'zcode-3.16.2-1-x86_64.pkg.tar.zst'` and the openssl twin → no output). So rollback of those foreign packages would require a rebuild from the AUR, not a cache reinstall.

9. [obs] A weekly `paccache.timer` is enabled and active (`systemctl list-timers`, `UnitFileState=enabled`, `Persistent=yes`, `NextElapseUSecRealtime=Mon 2026-10-26 00:00:00 -03`). Its unit runs `ExecStart=/usr/bin/paccache -r $PACCACHE_ARGS` with `PACCACHE_ARGS=` empty in `/etc/conf.d/pacman-contrib`, i.e. `paccache -r` with the default keep=3. The service's journal has no entries and `ExecMainStartTimestamp` is empty, so whether it has ever executed is not recorded ([unk]); the standing policy it encodes is keep-newest-3 per package, weekly.

10. [inf] Implication for rollback by cache after the pause is lifted: even after packages are re-downloaded, rollback-by-cache is bounded to the three newest versions per package by the weekly timer, and any manual `paccache -rk1` or `pacman -Scc` reduces it further to zero. The operator's decision to keep the Snapper fallback (as the corpus draft's P5 verdict says) is the only durable path; the cache gives no rollback today because it holds zero package archives.
