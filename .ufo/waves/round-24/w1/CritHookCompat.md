# CritHookCompat — attack on C2/P3 (round 24, attempt 2, wave 1)

Verdict: the claim "two completed boots on 42.2 images show the /new_root hooks are harmless" is falsified as an argument. Neither boot could show it, because both hooks fail silently and btrfs-overlayfs returned early on both boots. Per hook, the strongest supported verdicts are: plymouth `cleared` on the main linux entry, but only once the capture carries the evidence (it does not today), and btrfs-overlayfs `unverified`. The premise P3 as a single gate verdict must not be `cleared`.

## Counterexample

The limine entry `Omarchy.Snapshots.2026-10-20-09-29-19.linux` boots the byte-identical mkinitcpio 42.2 image that booted today (sha256 `2e9c9bdc…`). It boots it into snapshot 2 with `rootflags=subvol=/@/.snapshots/2/snapshot`, and that subvolume is `ro=true`. This is the only path on which btrfs-overlayfs does anything, and no boot has ever taken it on a 42.2 image. The two completed boots used `rootflags=subvol=@`, so the hook returned at its line 14 before it touched `/new_root` in any way that matters.

## Findings

1. [obs] Both hooks run as late hooks, after the 42.2 init has mounted root at `/sysroot`. The booted image's `config` has `LATEHOOKS="plymouth btrfs-overlayfs"`, and the image holds `new_root -> sysroot` (a relative symlink) plus `VERSION` = `42.2`. Evidence: `/usr/lib/initcpio/init:67` (`"$mount_handler" /sysroot`), `:71` (run_latehook) and `:110` (`switch_root /sysroot`). Also `lsinitcpio -x` of the `.initrd` section extracted from `/boot/EFI/Linux/omarchy_linux.efi` (exit 0), whose output shows `lrwxrwxrwx … new_root -> sysroot` and `LATEHOOKS="plymouth btrfs-overlayfs"`. The capture lines 93, 94, 106–112 and 117 in `/home/vgpnk/Projects/shokunin/tsukuroi-shokunin/.ufo/waves/round-24/capture/l1/capture.txt` agree.

2. [obs] A late-hook failure leaves no trace in a completed boot. `run_hookfunctions` calls `"$fn"` and never checks its status (`/usr/lib/initcpio/init_functions:88-101`). The `:: running late hook` message is suppressed by `quiet`. The booted command line has `quiet splash loglevel=0` and no `rd.log`/`rd.debug`, so `rdlogger_start` (`init_functions:443`) logs nothing and the initramfs stage never reaches the journal. Every failure branch of btrfs-overlayfs ends in `return 0` (`/usr/lib/initcpio/hooks/btrfs-overlayfs:7,8,11,14,18,19,24-54`). Evidence: `cat /proc/cmdline` (exit 0, fields as listed, with the secret-bearing fields redacted).
   [inf] So "the boot completed" does not tell hook success apart from hook skip for either hook. The capture lines 136–167 cited for P3 are systemd-stage units only (plymouth-start, plymouth-read-write and plymouth-quit after switch_root). They cannot show the result of `plymouth update-root-fs --new-root-dir=/new_root`. Citing them for "harmless" is false provenance.

3. [obs] Which entry booted and which image. EFI variables for boot 0: `LoaderEntrySelected` = `Omarchy.linux`, `LoaderImageIdentifier` = `EFI\Linux\omarchy_linux.efi`, `LimineLastBootedEntry` = `Omarchy/linux`, `LoaderInfo` = `Limine 12.9.3`. Source: `/sys/firmware/efi/efivars/*-4a67b082-…` and `*-513ee0d0-…`, read directly. The `b2sum` of the booted file starts `822299bbdaf0d4ede97d341fd5fcfa73fb3ca394`, which matches the hash pinned in the `Omarchy/linux` entry path in `/boot/limine.conf` (read with `sudo -n`, only entry names, paths and the `rootflags=subvol=` field kept). `lsinitcpio -a` on its `.initrd` reports `Created with mkinitcpio 42.2`, kernel `7.2.11-arch1-1`. The hook files and `findmnt` inside the image are byte-identical to the host copies (`cmp`, exit 0 for each).
   [inf] Boot -1 (2026-10-20 09:57:09 -03) left no loader variables, because each boot overwrites them. It used kernel 7.2.11 and `rootflags=subvol=@` (`journalctl -b -1 -k`, "Command line"), and the only 7.2.11 entry with `subvol=@` is `Omarchy.linux`. The file's mtime of 2026-10-20 09:26:22 is earlier than 09:57:09, so boot -1 most likely booted the same image.

4. [obs] Provenance detail for "42.2 images": mkinitcpio was upgraded 41.1-1 → 42.2-1 at 2026-10-20T09:16:29 (`/var/log/pacman.log:2539`), and the pacman hook built both UKIs at 09:18:14–09:18:24 (`pacman.log:2984-3047`). The file now on disk is newer (09:26:22). It was rebuilt by a manual run at 2026-10-20T09:26:11 -03, where user vgpnk ran `sudo` with command `limine-update` and no flags, outside the fleet repo (`journalctl _COMM=sudo`). mkinitcpio 42.2 was still installed, so the image is still 42.2 (finding 3). The linux-lts 42.2 image (`omarchy_linux-lts.efi`, `Created with mkinitcpio 42.2`) has never booted: both post-upgrade boots ran 7.2.11.

5. [obs] btrfs-overlayfs did nothing on either boot. The root source is `/dev/mapper/root[/@]` (`findmnt -no SOURCE /`; capture line 21 shows `subvol=/@`), which does not match `*/snapshot*` (`hooks/btrfs-overlayfs:12-14`). The snapshot path exists and is armed: snapshot 2 (`otime 2026-10-20 09:29:19`) and snapshot 1 are both `ro=true` (`sudo -n btrfs property get -t subvol /.snapshots/{1,2}/snapshot ro`, exit 0). The `09:29:19` linux snapshot entry points at `limine_history/omarchy_linux.efi_sha256_2e9c9bdc…`, the same sha256 as the booted UKI. Only boots -1 and 0 started after 09:29:19 (`journalctl --list-boots`), and both used `subvol=@`. So no read-only snapshot boot on a 42.2 image has happened.

6. [obs] The symlink works for the mechanism outside a real boot. I ran an unprivileged namespace test (`unshare -rmpf --propagation private`, chrooted into the extracted booted initramfs, using its own busybox ash, findmnt, btrfs and mount), with `/home` (btrfs `@home`) bind-mounted on `/sysroot`. `findmnt --mountpoint /new_root -no FSTYPE,SOURCE` printed `btrfs /dev/mapper/root[/@home]` (rc 0), the same as for `/sysroot`. `btrfs property get -t subvol /new_root ro` printed `ro=false` (rc 0). The hook's own sequence then ran: `mount --move /new_root <lowdir>` gave rc 0, and an overlay mount on `/new_root` gave rc 0, after which `findmnt --mountpoint /sysroot` shows `overlay`. So the overlay lands where `switch_root /sysroot` will look. A probe write went to the tmpfs upper only; the lower directory has no probe file.
   [unk] The test could not exercise the `ro=true` branch, a real snapshot `rootflags` mount with `rw`, or the `encrypt` and `resume` early hooks. Doing that would need a snapshot boot, which this round forbids. For btrfs-overlayfs this is mechanism-level evidence only, not boot evidence.

7. [obs] plymouth evidence that does exist: on boot 0, plymouthd wrote into the real root at quit time. `/var/log/boot.log` has mtime 2026-10-22 04:55:44.143 and `/var/lib/plymouth/boot-duration` has 04:55:44.152 (`stat`, exit 0). The journal has `Starting Terminate Plymouth Boot Screen` at 04:55:44.140 (`journalctl -b 0 -o short-iso-precise`). The responding daemon is `PID 535 (plymouthd)` (capture line 146). The root filesystem's first mount in the initramfs was done by `mount (942)` (`journalctl -b 0 -k`: `BTRFS: device fsid … scanned by mount (942)`). On boot -1 the corresponding numbers are 538 and 946. The installed plymouthd carries `on_newroot`, which imports `chdir` and `chroot` and has the string `new root mounted at "%s", switching to it` (`strings`, `nm -D /usr/bin/plymouthd`).
   [inf] A PID below the root-mount PID means plymouthd was started by the initramfs `run_hook`, before root was mounted. If its `update-root-fs` to `/new_root` had failed, its root would have stayed in the discarded initramfs, and `boot.log` would not have changed on disk. So the symlinked `/new_root` worked for plymouth on boot 0. Boot -1 rests on the PID ordering alone, because its `boot.log` was overwritten.

8. [inf] There is a limit on plymouth on snapshot boots that is not new in 42. Plymouth's late hook runs before btrfs-overlayfs (`LATEHOOKS` order), so plymouthd chroots into the read-only snapshot mount before that mount is moved under the overlay. Its later `boot.log` writes would then hit the read-only lower layer. The order and the logic were the same under 41.1 (the snapshot 1 image is `Created with mkinitcpio 41.1` and has a real `new_root/` directory), so this is not a 42 regression and does not block the gate. The gate limits should still name it, so that a future "plymouth cleared" is not read as covering snapshot boots.

9. [unk] `/boot/limine.conf` mtime is 2026-10-22 05:05:38, which is after boot 0 started (04:55:41). The boot configuration was rewritten during this boot, by an actor I did not identify. The linux entry hash still matches the booted file (finding 3). Any boot-chain claim should be pinned to the entry hash, not to the file's mtime.

## Impacted axes

- freshness (the C2 axis): the P3 evidence is stale or mis-sourced if it rests on capture lines 136–167.
- calibration: a `cleared` verdict would claim more than the evidence shows (premature saturation).
- provenance: the journal lines cited show the systemd stage, not the late-hook outcome.

## Smallest safe correction

1. Give P3 the verdict `unverified` (or `changed` only if `limits` says that the btrfs-overlayfs read-only-snapshot path is unexercised on 42.2 and that linux-lts 42.2 never booted). Never use `cleared`.
2. Put the per-hook split in `limits`: plymouth is cleared on `Omarchy.linux` (boot 0); btrfs-overlayfs is unverified, because it returned early at line 14 on both boots and is backed by namespace-level evidence only.
3. If plymouth is to count, the committed capture must gain lines it lacks today:
   - `stat -c "%y %n" /var/log/boot.log /var/lib/plymouth/boot-duration`;
   - the boot-0 kernel line `scanned by mount (942)`;
   - `lsinitcpio -a` of the booted UKI's `.initrd` (`Created with mkinitcpio 42.2`);
   - the `LoaderEntrySelected` and `LoaderImageIdentifier` values;
   - `btrfs property get` on `/.snapshots/2/snapshot`;
   - the snapshot entry's history-image sha256.

   Without these lines, no evidence row can satisfy the gate's "line exists and contains" rule for the plymouth part.
4. The canonical judge should reject any P3 `cleared` that cites only capture lines 136–167. This is a tradeoff the judge must reject, not a defect the author can fix by rewording.
