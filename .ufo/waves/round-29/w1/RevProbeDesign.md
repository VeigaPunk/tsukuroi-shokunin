# RevProbeDesign — C2 probe review (tools/probe-git-env-leak.py)

Partly holds: the probe reproduces the before-receipt exactly and never writes to the lane, but the frozen target list is provably incomplete — at least eleven more lane tool files perform git writes at the round-29 base and one of them has an unscrubbed `git init` — and detection rests on an exit-code diff with a fingerprint that cannot see several real write classes.

## Findings

1. **[high] Frozen list is not "every lane tool that runs git writes."** The docstring (tools/probe-git-env-leak.py:11-13) says the eight targets are "the tools whose source at the round-29 base `16e9ab2a` invokes a git write (`init`, `add`, `commit`; found by `grep -lE "'(init|commit|add)'|git (init|commit|add)" tools/*`)". That pattern only matches single-quoted literals `'init'|'add'|'commit'` or the contiguous text `git <verb>`. It misses every double-quoted invocation (`["git", "init", ...]`, `git("init", ...)`, `_selftest_git(repo, "init", ...)`), every `git -C <dir> init`, and every write verb outside init/add/commit (`update-ref`, `symbolic-ref`, `checkout`, `remote add`, `config`, `tag`, `hash-object -w`, `mktree`). Re-running the declared grep against `16e9ab2a -- tools/*` returns exactly the eight files; a broader scan at the same revision finds git writes in eleven more: tools/check-adjacency-anchors.py:971-985 (init/config/add/commit/update-ref), tools/check-boot-chain.py:1338-1386 (init/symbolic-ref/add/update-ref/checkout), tools/check-boot-writers.py:654-683 (init/config/add/commit), tools/check-recheck-commands.py:1081-1493 (init/config/add/commit/checkout/update-ref), tools/check-revision-binding.py:1122-1505 (init/add/commit/checkout/update-ref/symbolic-ref), tools/check-root-dac-correction.py:383-448 (init/add/commit/checkout/update-ref/remote add), tools/check-seat-scope.py:608 (update-ref in its selftest), tools/check-section-citations.py:595-610 (init/symbolic-ref/commit/checkout/remote add), tools/check-self-assessment.py:975-984 (init/add/commit), tools/check-source-scope-correction.py:517 (update-ref), tools/measure-update-recheck.py:518-608 (init/symbolic-ref/add/checkout/update-ref), and the helper tools/_revision.py:220-417 (init/commit/checkout/tag/update-ref/hash-object -w/mktree, selftest). The two shell tools named in my assignment are clean: `git` appears in tools/boot-chain-audit.sh zero times and in tools/tsukuroi-census.sh only inside comments about printf format tokens (`%04a`, `0555`); grep finds no git invocation. Most omitted Python tools scrub GIT_* inside their git wrappers, so the omission is a coverage defect of the counter, not proof of more leaks — but "the eight lane tools that run git writes" (SCORECARD.md round-29 declaration) is false as a statement about the base tree.

2. **[high] A real leak sits outside the frozen list.** tools/check-self-assessment.py:975 runs `subprocess.run(["git", "init", "-q", repo], check=True)` with no `env=` — it inherits GIT_DIR/GIT_WORK_TREE/GIT_INDEX_FILE — while its later `add`/`commit` (lines 982-984) pass the scrubbed `git_env()`. Verified behaviour: with GIT_DIR pointed at a canary, `git init -q <dir>` exits 0, reinitializes the canary's .git (no HEAD/object/ref change — see finding 3), creates the target directory empty, and then `git -C <dir> add -A` under the scrubbed env fails ("not a git repository") → CalledProcessError → nonzero exit. So this tool both follows the inherited env and crashes — it would score `leak: true` had it been a target. Evidence: line 975 has no env argument; reproduction in /tmp/rpd-canary + /tmp/rpd-newrepo (init-rc=0, HEAD still `ref: refs/heads/canary`, new dir empty).

3. **[medium] All three receipt leaks are detected only by the exit-code diff; the fingerprint is blind to the writes actually exercised.** Receipt lines 1, 7, 8 all show `"canary_changed": false` — `git init` under GIT_DIR reinitializes the canary in place (verified: exits 0, HEAD unchanged, no object written) and `git add -A`/`git commit` under GIT_WORK_TREE=canary see only the unchanged CANARY file, so the only signal is the tool's later crash. The fingerprint (probe lines 67-81) covers objects/, refs/, HEAD, index, packed-refs but not `.git/config`, `.git/logs/`, `.git/hooks/`, `.git/info/`, `.git/shallow`, `COMMIT_EDITMSG`, `ORIG_HEAD`, `.git/worktrees/`, or the canary's worktree files themselves. A tool whose only inherited-env writes are `git init` (reinit, exits 0) plus `git config` (writes .git/config, unfingerprinted), or `git clean`/`checkout` that rewrite the CANARY worktree file without touching .git, would produce `canary_changed=false` and — if it exits the same code as control — `leak: false`: a false negative. The "same exit code by chance" gap named in my assignment is real: the probe's `leak` is `canary_changed or canary_rc != control_rc` (line 156), so a leaking tool whose canary run happens to exit 0 (or a control run that happens to be flaky) passes silently.

4. **[medium] The exit-code criterion also yields false positives against the claim's own semantics.** Any behavioural difference counts: a tool that deliberately refuses to run when GIT_DIR is set (a correct containment posture) exits nonzero and is reported `leak: true` though it followed nothing and wrote nothing; a tool that performs a pure read (`git rev-parse`, `git for-each-ref`) against the canary and exits differently is likewise flagged. The docstring (line 24) owns this — "the tool's git reads or writes followed the inherited variables" — so `leaking` counts env-followers, not write-leakers; that matches the claim's wording "no longer follow an inherited GIT_DIR" but is broader than the round-28 incident (commits landing in the lane). Reviewers of the after-receipt should not read `leaking` as a count of tools that can commit into a foreign repo.

5. **[low] The probe does not touch the lane; containment checks out.** Every git invocation goes through `run()` with `clean_env()` (GIT_* stripped, GIT_CONFIG_NOSYSTEM=1): `git -C <lane> rev-parse --verify` (read), `git -C <lane> archive <rev>` (read), `git clone -q --bare --no-local <lane> <scratch>/lane.git` — reads lane objects, writes only inside scratch. The commonpath guard (lines 106-108) refuses a scratch inside the lane; `shutil.rmtree(root)` removes only the probe's own mkdtemp tree. `probe_sha256` reads its own `__file__`. One side note: the probe itself performs git writes in `make_canary` (init/add/commit) and — added at the declaration commit — matches its own screening grep at the tip (`git grep` at `81a061a` lists it ninth); it is excluded from TARGETS, so the frozen list is "all at-base writers except the probe that measures them," which is reasonable but means the C2 counter can never observe a leak in the probe itself.

6. **[low] Timeout handling asymmetry is a minor doc/code mismatch.** A control timeout is a harness error (line 131); a canary timeout sets `canary_rc='timeout'` and is scored `leak: true` (lines 152-156) — a harness-level stall is counted as a leak. At 900 s per run this is unlikely, but a wedged selftest would be reported as a leak rather than an error.

## Residual risk and gaps

- The C2 declared after-value (`leaking` 0 of `targets` 8) can be met without finding 2's unscrubbed `git init` in check-self-assessment.py ever being observed; if the claim is read as "every lane tool that runs a git write," the fix must either widen TARGETS or justify the exclusion.
- If wave-2 fixes the three leakers only by making them exit nonzero under GIT_* (refusal), the counter still reports `leaking` > 0 — the fix must scrub the env, and a seat verifying the after-value should confirm `canary_changed=false` + `canary_rc=control_rc`, not just reread the summary.
- Nondeterministic tools (timing, ports) could flip `leak` between runs with no code change.
