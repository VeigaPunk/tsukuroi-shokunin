# RevF7Quant — row F7 vs the v7.2 oom_badness rule (Tsukuroi R29, wave 1, seat RevF7Quant)

**Verdict: holds.** F7 (SKILL.md:1094) is quantitatively correct in the only kernel-kill domain reachable on this host (global OOM), and it holds with a sharper reason than the row states: the +100-vs-+200 gap is worth 1,690,900 pages ≈ **6.45 GiB of rss+swap+pgtables footprint** (10% of RAM+swap), a margin the manager provably could not clear. In a memcg-scoped OOM the same class facts would **not** decide the victim — but that path is measured-closed on this host, so the row's conclusion stands where it matters.

## Findings

1. **The formula, source-verified.** Fetched https://raw.githubusercontent.com/torvalds/linux/v7.2/mm/oom_kill.c (saved `.ufo/waves/round-29/w1/RevF7Quant/oom_kill.c`, sha256 `452f1348e79c252ee89215d55fb104591412bbcea4a3ee965e873a401f756b4e`). `oom_badness` (:199): `points = get_mm_rss_sum(p->mm) + get_mm_counter_sum(p->mm, MM_SWAPENTS) + mm_pgtables_bytes(p->mm) / PAGE_SIZE;` (:228-229), then `adj *= totalpages / 1000;` (:233) and `points += adj` (:234). Note the integer division lands inside the product: each +100 of oom_score_adj adds floor(totalpages/1000)×100 pages. Tasks at OOM_SCORE_ADJ_MIN are skipped (:217-219) — +100 is not skipped. Quote checks: each quoted line `grep -cF` = 1 [obs].
2. **The domain numbers, recorded.** Global: `oc->totalpages = totalram_pages() + total_swap_pages;` (oom_kill.c:263). MemTotal 31,721,780 kB → 7,930,445 pages [inf: totalram_pages ≈ MemTotal/4] from kill-event-deep-r8.md:182; Total swap 35,917,176 kB → 8,979,294 pages from oom-event-plane.md:82 (event A's own dump). Global totalpages = 16,909,739, unit = 16,909 pages. So +100 → 1,690,900 pages = 6.45 GiB; +200 → 12.90 GiB; +300 → 19.35 GiB. Page size 4 KiB confirmed by the dump's exact kB↔page pairs (27,873,696 kB / 6,968,424 pages, oom-event-plane.md:68 vs :106) [obs].
3. **Global OOM — would the kernel ever pick the +100 manager over a +200 client? No.** Manager beats candidate c iff foot_m − foot_c > 1,690,900 pages, i.e. the manager must hold > 6.45 GiB more footprint than that client. Recorded sizes exclude it: event A's task table (164 rows, oom-event-plane.md:98) shows the victim python3 at adj 200 with 6,968,424 anon + 7,110,160 swapents + 27,732 pgtables pages (:106, :68), while the other 163 tasks combined held only 7,140,787−6,968,424 + 8,228,965−7,110,160 = 1,291,168 pages = 4.93 GiB of anon+swap (aggregates :99-100). The manager's anon+swap was therefore below the 1,690,900-page threshold even had it held the entire residual. For the conclusion to flip, the manager's unrecorded file-rss+pgtables would need > 399,732 pages (1.52 GiB) [unk, implausible for a systemd --user instance]. The model also reproduces the observed pick: python3's points = 6,968,424+7,110,160+27,732+3,381,800 = 17,488,116 pages, vs a hard upper bound of 1,291,168+5,072,700 = 6,363,868 for any other task even granting one of them the whole residual and +300 — the observed victim is the formula's argmax [obs+inf].
4. **Memcg OOM scoped to a cgroup holding the manager — yes, the manager can be picked; the class argument does not transfer.** Two independent reasons: (a) *scan set*: a memcg OOM iterates `mem_cgroup_scan_tasks(oc->memcg, oom_evaluate_task, oc);` only (oom_kill.c:366-367), so +200/+300 clients in sibling cgroups are not candidates at all — the manager wins whenever it tops its own cgroup, class map irrelevant; (b) *shrunk handicap*: inside a shared cgroup, `oc->totalpages = mem_cgroup_get_max(oc->memcg) ?: 1;` (:258) [inf: the cgroup's limit budget; the definition lives in mm/memcontrol.c, whose fetch hit GitHub 429], so each 100 adj points are worth 10% of the limit: 52,400 / 104,800 / 209,700 pages = 204.7 / 409.4 / 819.1 MiB at L = 2 / 4 / 8 GiB. The manager is picked iff it out-holds the client by more than that — routine for a heavyweight manager vs small clients; for a limit under 1000 pages the floor at :233 makes the adj term vanish entirely. Additionally, with `memory.oom.group`=1 the whole hit cgroup dies irrespective of score (`oom_kill_memcg_member`, :1000, :1049-1052).
5. **Why F7 still holds: the memcg path is measured-closed here.** `memory.max`/`memory.high`/`memory.swap.max`/`memory.zswap.max` all `max` and `oom.group` 0 on the whole path (kill-event-deep-r8.md:244), **0** `Memory cgroup out of memory` prints in 13 boots (:30), and the single kernel kill in retention was `constraint=CONSTRAINT_NONE,…,global_oom` (oom-event-plane.md:63-66). The only reachable kernel domain is global, and in that domain the quantitative answer is no — the kernel would never pick the +100 manager while any +200 client lived. F7's stance survives; §4's wording "the scan prefers the higher-scored, larger-RSS tasks first" (kill-event-deep-r8.md:147) is direction-only, and this review supplies the missing magnitude [obs+inf].
6. **Timing caveat — the one way F7 could mislead.** The shield exists only while a +200/+300 task is alive. The recorded two-stage sequence puts the app purge *after* the manager's death (kill-event-deep-r8.md:219-222: session scope empty at .360829, manager dead ~.3808, `KillMode=mixed` teardown purges the app scopes last), so at the hypothetical pick instant the +200/+300 band (event A's table: 120×200, 15×300, oom-event-plane.md:115; live band map kill-event-deep-r8.md:141-142) was present [inf from the recorded ordering]. Had the band already exited, the +100 manager (adding 6.45 GiB while carrying tens of MiB) would top the +0/−x root band (kill-event-deep-r8.md:143-144) and a global pick of the manager would have been possible. F7 is an argument about a scored pick, not a proof that the kernel never kills +100 processes.
7. **`oom_kill_allocating_task` bypass checked.** Global-only and adj-guarded: `if (!is_memcg_oom(oc) && sysctl_oom_kill_allocating_task && … && current->signal->oom_score_adj != OOM_SCORE_ADJ_MIN)` → kills the allocating task with print `Out of memory (oom_kill_allocating_task)` (oom_kill.c:1145-1151). Default 0: `static int sysctl_oom_kill_allocating_task;` (:57, static uninitialized). Event A's observed print is the standard scored-path form `Out of memory: Killed process 1732581 (python3) … oom_score_adj:200` (oom-event-plane.md:67-68), so the bypass was off at event A. Its live value at event B is unrecorded (kill-event-deep-r8.md:262 lists oom_dump_tasks/panic_on_oom only) [unk] — moot, since event B has no kernel record at all (F1, kill-event-deep-r8.md:30).

**Verdict restated:** F7 **holds** — with the sharpened reason that its force is a 6.45 GiB-per-100-points margin in the global domain (the only reachable one on this host), not an absolute bar; in a memcg-scoped domain the same class facts would not decide the victim, but measurement (kill-event-deep-r8.md:244, :30) closes that domain.
