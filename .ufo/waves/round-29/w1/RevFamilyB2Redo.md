4. [obs] Boundary correctness of B2: the digest/pin-byte checks and the live-sibling cat-file comparison (check-adjacency-overlap.py:172-183) run only inside the spath == PIN_PATH branch, which is the only branch where a snapshot is fetched at all — a non-pinned sibling_path never reaches quote or byte checks but is already a refusal, so nothing escapes. altered-pinned-snapshot is refused even with no sibling repository (no-sibling pass: snapshot-not-pinned-bytes on all six rows, anchored 0), so the pinned-sha256 half of A2 does not secretly depend on the sibling checkout; the docstring claim on lines 41-44 ("which B2 plus the pinned sha256 make safe") is honest.

5. [inf] Two diagnostics inside the first B2 branch are dead for accept/refuse purposes: `not spath` and `'..' in spath.split('/')` (check-adjacency-overlap.py:159). Any value reaching that test is either equal to PIN_PATH (and so non-empty, dotdot-free by construction) or fails the sibling-path-not-pinned check anyway — a path that is invalid AND non-pinned reports only sibling-path-invalid, and every invalid path is refused regardless. They affect only the reason label, never the verdict. Harmless, but the battery exercises them as if they carried weight: sibling-path-dotdot reports sibling-path-invalid, not not-pinned, in both counters.

6. [obs][inf] The `snapshot` field check is decorative. The fetched snapshot path is always SNAP_DIR + spath (line 167), and under the pinned spath the check reduces to row['snapshot'] == a constant (line 164). It can only ever refuse rows that point at the pinned path anyway; no row could route the fetch through the field. That matches B2's wording ("`snapshot` names its committed copy"), but the check buys nothing the pinned-path equality does not already give — it is refusal-only redundancy, not a hole.

Summary shows should_pass_accepted 4, so a reader could mistake refused should-pass rows for counter over-strictness; they are stale labels, not counter defects.
