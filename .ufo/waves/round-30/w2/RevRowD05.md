# RevRowD05 — C1 row D05 attack report (revision 29bf87fa3971df04cb96e4ad9a28805d8154ed2f)

Verdict: partly holds. Snapshot integrity, quoted line, host reading, row mechanics and the read-only operator decision all verify; the factual core is sound. The defects are precision-level: the row's "reclaimable-space percentage" mirrors upstream wording that is inverted relative to the kernel arithmetic in the lane's own mined S159, and the SKILL line's "relocates" is not supported by the two cited lines.

## Findings

1. **[medium-low, wording vs kernel behaviour] "reclaimable-space percentage" is inverted relative to the kernel code.** S154 line 168 says "Reclaimable space percentage of block group's size (excluding permanently unusable space) to reclaim the block group." and D05/SKILL repeat "reclaimable-space percentage". Upstream kernel v7.2 (sha256-verified `fs/btrfs/block-group.c`, fetched to `/home/vgpnk/Projects/shokunin/tsukuroi-shokunin/.ufo/waves/round-30/w2/RevRowD05/v72-block-group.c`, sha256 `33779b4f6f6072f30eb38f8ac67a4c7b820210a5096b2cf999a0ad4c4ea834e8`) computes `thresh_bytes = mult_perc(bg->length, thresh_pct)` (line 1922, `mult_perc` = `num * percent / 100` in v72 misc.h line 109, fetched sha256 `c9bd2180771a4a1d13bfa4e49456d63d3e02ebd70e625c4843a7844985116d33`) and marks a group when its **used** bytes drop **below** p% of its length: `should_reclaim_block_group` rejects when `old_val < thresh_bytes` and when `new_val >= thresh_bytes` (lines 1933-1936); the committed S159 snapshot (sha256 `5654929f…`, byte-identical to upstream v7.2 space-info.c, verified this run) shows the same predicate at `/home/vgpnk/Projects/shokunin/tsukuroi-shokunin/.ufo/waves/round-30/w1/ScribeSrcSpaceInfo/S159-space-info.c:2155` ("if (bg->used < thresh && bg->reclaim_mark)"). So the knob is a used-space ceiling: p=75 reclaims groups over 25% free, not groups reaching "75% reclaimable". [inf] The doc's own top-level entry says "Used space percentage of total device space" (S154 line 41), so the per-type "Reclaimable space percentage" wording is inconsistent even inside S154. Suggested SKILL col-2 wording: "`allocation/<type>/bg_reclaim_threshold` is the used-space percentage below which the kernel relocates a whole block group". Suggested statement wording: "…holds percentage p; the kernel marks a block group for reclaim when its used bytes fall below p percent of its length, then relocates the whole group…".

2. **[low, citation gap] "relocates a whole block group" is true but not in the cited lines.** S154 lines 168-169 say only "to reclaim the block group". Kernel truth: `btrfs_reclaim_block_group` calls `btrfs_relocate_chunk(fs_info, bg->start, false)` (v72-block-group.c line 2049), and S159 line 1416 reads "reclaim_bgs_list and check if we can relocate them" — but that comment describes the zoned flush state, not the regular-device path (the regular path is the `!alloc && reclaim` marking at block-group.c lines 3938/3963-3964, outside the cited corpus). Fix: either cite the kernel lines or use the doc's verb "reclaims".

3. **[low, missed knowledge] The `[unk]` on the meaning of 0 is weaker than the lane's own mined material.** With `dynamic_reclaim` 0 (host-verified this run: `/sys/fs/btrfs/1d02a454-…/allocation/metadata/dynamic_reclaim` = 0, `periodic_reclaim` = 0, `reclaim_count` = 0 [obs]), `btrfs_calc_reclaim_threshold` returns the knob itself (S159 lines 2115-2117) and the sweep predicate `bg->used < thresh` cannot hold at thresh 0 on a u64 (S159 lines 2154-2155); upstream also short-circuits `if (thresh_bytes == 0) return false` (v72-block-group.c line 1926). So "0 disables threshold-based reclaim marking" is derivable from S159, which this JSON already cites in `supporting_citations`. Statement's "what 0 means is not stated by this chapter" is literally true but could have been resolved. [obs] The dirty worktree (HEAD 32e5d848, uncommitted changes to SKILL.md) already moved the SKILL cell toward exactly this fix; this review judges the committed bytes at 29bf87fa.

4. **[nit, upstream doc] "(RW since: 5.19)" in the SKILL parenthetical.** S154 tags the per-type file under `allocations/` "since: 5.19", yet sibling files in the same directory are "since: 6.11" (dynamic_reclaim line 202, periodic_reclaim line 219) and 5.19 is the vintage of the *global* `/sys/fs/btrfs/UUID/bg_reclaim_threshold` knob (S154 lines 38-42, "Mostly for zoned devices"). [inf — likely an upstream copy-over; I did not fetch per-kernel sysfs.c history to pin the exact version.]

5. **[nit] "(excluding permanently unusable space)" vs kernel.** Both call sites multiply the full `bg->length` (S159 line 2154; block-group.c line 1922); no zone_unusable term is subtracted. On non-zoned devices zone_unusable is 0 so the distinction is vacuous here [inf].
