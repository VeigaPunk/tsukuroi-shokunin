# SentinelProbeHollow — can a lane tool reach `leaking 0` while still following a residual channel?

Verdict: partly holds. The declared C2 after-value is genuine for the eleven tools' own git children: no hollow fix was found — under both the `--selftest` argv and the production (`--revision`) invocation, every target's exit code, normalised stdout, git-child count and every git child's own `HOME`/`PATH`/`GIT_CONFIG_GLOBAL`/`GIT_CONFIG_NOSYSTEM`/`GIT_CEILING_DIRECTORIES` are identical to the clean control, in all three frozen channels. But `leaking 0` is still reachable while residual channels are live: 2 of the 11 targets leave 743 and 872 git children of a child process outside the contract, `LD_PRELOAD` still executes inside every git child, and a dropped `.git` pointer is still followed by the tip's own environment builder.

## Method, and why the negative result is load-bearing

1. [obs] Instrumentation. `gitspy.c` (sha256 `bd507e7d…`) is an `LD_PRELOAD` constructor that, for every process whose `/proc/self/exe` basename is `git`, appends one tab-separated line to `$SPY_LOG`: its own `HOME`, `PATH`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM`, `GIT_CEILING_DIRECTORIES`, `LC_ALL`, cwd and `LD_PRELOAD`. `hollow.py` (sha256 `cbfa1fbe…`) runs each target four ways (control, `user-files`, `path-wrapper`, `enclosing`) and records rc, **normalised stdout digest** (40-hex and 64-hex and the scratch root normalised), git-child count, per-child contract variables, hostile hook log lines, and a **widened** canary fingerprint that adds `.git/config`, `hooks/`, `info/`, `logs/` to the probe's field set (`/home/vgpnk/Projects/shokunin/tsukuroi-shokunin/.ufo/waves/round-30/w2/SentinelProbeHollow/hollow.py:104-155`). The two additions are exactly the two counters wave 1 showed the probe lacks (`probe-git-env-residual-r30.py:246-251` compares only the canary log and the exit code; `:89-103` is the narrow fingerprint).

2. [obs] Spy completeness check, so that "0 non-contract children" is not a blind spot of my own. `strace -f -e trace=execve` on `check-kernel-taint.py --selftest` gives 877 `execve("/usr/bin/git"` plus 56 `execve("/usr/lib/git-core/git` = 933 execs; the spy recorded exactly 933 children for the same run. Exit 0. No git exec escapes the spy, including absolute-path and `PATH=/usr/lib/git-core` self-execs.

3. [obs] One artefact in my own table: the three `enclosing` deltas in `runs/production-checks.jsonl` (`check-freshness-r17`, `check-memory-pressure`, `check-registry-coverage`: rc 2 vs 0) are a harness artefact, not a leak. In production mode the tool is run from inside the sandbox clone (`--repo <clone>`), while the enclosing variant runs the copy inside a fresh canary repo that has no history, so the tool returns CANNOT_EVALUATE before its inputs exist. The same targets in the channel the probe actually uses (`--selftest`) show no delta. I discount these three rows.

6. [obs] **Two of the eleven still have git children outside the contract — invisible to the probe.** In the two owed-statements batteries, 743 of 900 children (`mutants-owed-statements-r29`) and 872 of 1044 (`mutants-owed-statements-r29-landed`) run with `GIT_CONFIG_GLOBAL=-`, `GIT_CONFIG_NOSYSTEM=-` and no `GIT_CEILING_DIRECTORIES`, in every variant, identical count in control and in both channels (`runs/batteries.jsonl`; 2972 and 3488 records over four variants). Their `HOME` is the battery's private dir and their `PATH` is `/usr/bin:/bin`, inherited from the battery's sanitised `ENV`, but the contract keys were stripped and not re-added by the counter child:
   - `tools/check-owed-statements-r29.py:133-137` — `env = {k: v for k, v in os.environ.items() if not k.startswith('GIT_')}` then `env.update({'GIT_OPTIONAL_LOCKS': '0', 'LC_ALL': 'C'})`, and `:139-140` is the only git site: `subprocess.run(['git', '-C', lane, *args], ..., env=clean_env(), ...)`.
   - Why the probe reads 0: none of the three frozen channels can reach these children. The hostile ignore file lives under `HOME`/`XDG_CONFIG_HOME`, which stay private; `PATH` is already `/usr/bin:/bin`; and discovery is anchored by `-C <clone>` (the battery's own clone), not by the process cwd. So `leaking 0` is correct for the frozen channels and wrong for the claim's own docstring wording "every subprocess follows the round-30 git child environment contract" (`tools/mutants-owed-statements-r29.py:11-13`).
   - Live surface today: only the system config scope, since `GIT_CONFIG_NOSYSTEM` is unset; `/etc/gitconfig` does not exist (`ls: cannot access '/etc/gitconfig': No such file or directory`), so it is inert [inf]. The missing ceiling is also inert here because every call carries `-C` to a real clone [inf]. This is a latent hole, not a live leak, and it is the same class wave 1 flagged for the counter's own reads.

7. [obs] **`LD_PRELOAD` is still live at the tip (SentinelGitEnv3 finding 1 re-confirmed).** My own spy is the attack: setting `LD_PRELOAD=<gitspy.so>` in the ambient environment made attacker code run in **933 of 933** git children of `tools/check-kernel-taint.py --selftest`, with exit 0 and stdout byte-identical to control (`b06bcb2491bd740d`, 8706 bytes). The contract builder copies `os.environ` and drops only `GIT_*` (`tools/check-kernel-taint.py:249-266`), so every `LD_*`/`PYTHONPATH`-class variable survives; `PATH=/usr/bin:/bin` does not touch it because the loader resolves `LD_PRELOAD` by path. The probe's three channels cannot see this and are not meant to.

8. [obs]/[unk] **Dropped `.git` pointer still followed (SentinelGitEnv3 finding 2 re-tested with the tip's own builder).** `dotgit.py` (sha256 `c0264a2a…`) imports `git_env` from the tip's `check-kernel-taint.py` and runs it in a directory whose `.git` is a `gitdir:` pointer at an attacker repo:
   - `git status --porcelain` rc 0, prints `?? payload`; `git add -A` rc 0; `git commit -qm pwn` rc 0, and the attacker repo's HEAD becomes `pwn` with `git status` `D payload`. The contract's ceiling does not help because the pointer sits at the working directory itself.
   - `git init -q` over the same pointer exits 0 and leaves `.git` a pointer file (`init_left_pointer: true`).
   - Lane shape [unk]: planting the pointer in the tool's working copy and running the target's `--selftest` gave `attacker_mutated: false` for `check-kernel-taint`, `check-freshness-r17`, `check-storage-health`, `check-registry-coverage` and `check-self-assessment`, all rc 0. So I found no write exploit through these five; their selftests write only in their own fixtures. Reads from a pointer-planted tree would still be redirected — not demonstrated as a verdict change, so untreated here.

9. [obs] **The probe's remaining blind spot is exactly the one that caught wave 1.** `probe-git-env-residual-r30.py:246-251` builds evidence only from the canary log and `channel_rc != ctl_rc`; there is no stdout comparison and no child-environment observation. My two additions catch both wave-1 hollow shapes (`hollow-skip` would be a 0-byte stdout, `hollow-swallow` an rc error swallowed but a 21767-byte hostile run) and would also catch finding 6 (the child-environment comparison). Nothing at this tip is hollow; the counter is simply unable to distinguish a future one.

10. [obs] Two tools close the shared helper by **mutating it at import**: `tools/check-registry-coverage.py:46` and `tools/check-storage-health.py:78` both run `_revision.clean_env = clean_env`, permanently replacing the attribute for every module imported after them in the same process. It is not a leak — the replacement is stricter — but it makes the correction depend on import order and quietly changes `_revision.clean_env` for anything else in the process. The declaration's separability sentence ("C2 changes only the eleven target tools", `SCORECARD.md` round-30 declaration) is still textually true for the file set, but the behavioural effect reaches past those two files [inf].

## Impact

Operability (C2): the declared `0 of 33` is real and not a hollow number for the three frozen channels, in both modes; I could not make any of the eleven reach 0 while a frozen channel steered a git child. What is overstated is the wider reading: 2 of 11 leave 743/872 git children outside the contract, and two named-outside-the-claim channels (`LD_PRELOAD`, `.git` pointer) remain wide open at the tip, so `leaking 0` must not be read as "no residual git-environment channel". There is no mutation of the lane from any of this: all runs were in the sandbox clone/export, the hypothesis repo and `/fast/scratch`.

## Smallest safe correction (report-only; no lane edit made)

1. Give the counter child the contract: in `tools/check-owed-statements-r29.py:133-137` re-add `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=os.devnull`, `GIT_CONFIG_SYSTEM=os.devnull`, a private `HOME`/`XDG_CONFIG_HOME` and `GIT_CEILING_DIRECTORIES` — or have the batteries pass their own `ENV` down and have the counter use it verbatim. This is the one change that makes the two batteries' "every subprocess" docstring true.
2. Drop `LD_*` (and `PYTHONPATH`/`PYTHONHOME`) in the contract builder, in the same place every tool already filters `GIT_*`; one shared line per builder.
3. Refuse a `.git` that is not a directory at the point a tool creates or reuses a sandbox (a `.git` file must be rejected outright); this is cheaper than trusting the ceiling.
4. If a later round widens the probe rather than the tools, add a stdout-digest comparison and a child-environment observer — these two would have caught all of wave 1's hollow mutants and would catch finding 6 today.
