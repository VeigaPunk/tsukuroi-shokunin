## B. Row-wording attacks

7. SH1, "the sysfs `error_stats` file and the `btrfs device stats` query report the same counters".
   - [obs] True in the kernel source. sysfs prints the five `btrfs_dev_stat_read(device, BTRFS_DEV_STAT_*)` values (`sysfs.c:2088-2098`), and the ioctl returns `btrfs_dev_stat_read(dev, i)` (`volumes.c:8488-8490`).
   - [obs] The names differ: sysfs says `write_errs`/`read_errs`/`flush_errs` (`capture.txt:40-42`), the ioctl tool says `write_io_errs`/`read_io_errs`/`flush_io_errs` (`capture.txt:112-114`).
   - [obs] Both can refuse: sysfs prints "invalid" when `!device->dev_stats_valid` (`sysfs.c:2080-2081`), and the ioctl returns ENODEV with "get dev_stats failed, not yet valid" (`volumes.c:8474-8476`).
   - [inf] The capture cannot prove "same counters". All ten values are 0 (`capture.txt:40-44,112-116`), and two all-zero readers agree whatever they read.
   - Correction: the "same" must cite S133/S132 code, not the capture. Say "the same five counters under different names", and add the `invalid` / not-yet-valid case.
8. SH2, "persist across mounts until an explicit reset … a dated incident comes from the kernel's per-error log line".
   - [obs] The incident line format is also printed at mount. `btrfs_dev_stat_print_on_load` logs "bdev %s errs: wr %u, rd %u, flush %u, corrupt %u, gen %u" at info level whenever any persisted counter is non-zero (`volumes.c:8438-8455`). It is called on every load (`volumes.c:8224`). S128 says the same: "The current values are printed at mount time and updated during filesystem lifetime or from a scrub run." (`device.rst:232-233`)
   - [obs] The capture's dated-incident probe greps `BTRFS.*errs: wr` (`capture.txt:155`), which matches both the error-level incident line and the info-level mount replay.
   - [obs] The incident print is rate-limited: `btrfs_err_rl` (`volumes.c:8428`). One line is therefore not one error.
   - [obs] Persistence happens at transaction commit: "called from commit_transaction. Writes all changed device stats to disk." (`volumes.c:8351-8352`). [inf] So increments since the last commit can be lost at a power loss. This host's controller reports 200 unexpected power losses (`capture.txt:196`).
   - [obs] A reset is itself logged: "device stats zeroed by %s (%d)" (`volumes.c:8485`). The capture never greps for it; its two greps only match `errs: wr` and `BTRFS (error|critical|warning)` (`capture.sh:39,41`). Zero counters therefore do not prove there was never an error within retention.
   - Correction: "persist across mounts (written at transaction commit) until a reset, which the kernel logs as `device stats zeroed`". Also: "an error-level `BTRFS error … errs:` line dates an increment (rate-limited); an info-level line of the same format at mount replays stored totals and is not an incident".
9. SH3, "with the data profile `single` a data checksum error is detected but not repaired, and the `dup` metadata profile keeps a second copy".
   - [obs] NOCOW files are not even detected. "setting the `NOCOW` file attribute … implicitly enables `NODATASUM` … the actual file data is not." (`ch-scrub-intro.rst:21-24`) This host's systemd 262-1 owns `/usr/lib/tmpfiles.d/journal-nocow.conf`, whose line 25 is `h /var/log/journal - - - - +C`. systemd v262 re-enables copy-on-write only when a journal file is archived (`src/shared/journal-file-util.c:201-213` at tag v262). [inf] Active journal files on `@log` (`capture.txt:23`) therefore have no data checksums. Scrub cannot verify them under any profile. [unk] Not confirmed per file, because `lsattr` is outside the read-only allow-list.
   - [obs] Inline file data follows the metadata profile. `max_inline` defaults to "min(2048, page size)" and is inlined "in a metadata b-tree leaf" (`ch-mount-options.rst:272-276` at v7.1). The capture's mount options set no `max_inline` (`capture.txt:26`). [inf] Small files are therefore stored `dup` on this host and can be repaired from the second copy, so `single` does not mean "never repaired" for every file.
   - [obs] Compression does not remove checksums: "Compression requires both data checksums and COW" (`ch-compression.rst:171-172`). Compressed data is therefore detected-not-repaired like other `single` data. [inf] One bad sector can make a whole compressed chunk of up to 128 KiB unreadable (`ch-compression.rst:10`).
   - [obs] `dup` is two copies on one device. "Whether there are really 2 physical copies highly depends on the underlying device type." (`mkfs.rst:635-637`) Wear levelling may put both into one physical unit (`mkfs.rst:657-661`). [inf] On LUKS (`capture.txt:31-32`) the per-sector IV gives the two copies different ciphertext. Device-level deduplication is then unlikely, but the wear-levelling caveat still applies.
   - [obs] Repair is not scrub-only: "Such automatic repair is also carried out when reading metadata or data from a read-write mounted filesystem." (`ch-scrub-intro.rst:17-18`)
   - [obs] Source impact: S129 is `btrfs-scrub.rst`, which pulls in this chapter through `.. include:: ch-scrub-intro.rst` (`scrub.rst:12`). The NOCOW and read-repair sentences are therefore not substrings of the committed `S129.rst`. A quote of them fails the C1 substring rule (`SCORECARD.md:897`) unless an S139 row snapshots `ch-scrub-intro.rst`. Inline and compression facts need their own rows as well.
   - Correction: "for checksummed data in `single` data block groups, scrub detects but cannot repair a checksum error; NOCOW (nodatasum) data is not verified at all; inline data follows the metadata profile; `dup` keeps a second copy on the same device".
10. SH4, "no scrub statistics exist … so stored data has never been verified end to end".
    - [obs] "No stats" means no userspace record: the status file is under `/var/lib/btrfs` (`scrub.rst:137-138`; `ch-scrub-intro.rst:71-72`), and that directory is absent (`capture.txt:126-128`).
    - [inf] A scrub run from another root, a rescue or live system, before a reinstall, or before a rollback of `@` would leave no record here. Neither would one recorded only in kernel journal lines older than the 6 retained boots (`capture.txt:161`). The capture greps prior boots only for error, critical and warning lines (`capture.sh:39,41`), not for scrub start or finish info lines. Only boot 0's BTRFS lines are printed (`capture.txt:166-173`), and none mentions scrub. [unk] The exact kernel scrub log strings, because `fs/btrfs/scrub.c` returned HTTP 429 from raw.githubusercontent.com.
    - [obs] `is-enabled` reports state at capture, not history (`capture.txt:130-132`).
    - [obs] Checksummed data is verified on every normal read (`ch-scrub-intro.rst:17-18`). "Never verified" is therefore false for data that was read. The lifetime read total is 85.3 TB (`capture.txt:189`), a device-level figure that may include non-btrfs reads.
    - [inf] "End to end" also overstates what even a completed scrub does here, because NOCOW journal data is excluded (finding 9).
    - [obs] Trap: the same output prints "Error summary:    no errors found" with no scrub on record (`capture.txt:121-124`). No row should cite line 124 as evidence of health.
    - Correction: "no scrub record exists in this root's btrfs-progs status directory and the monthly timer is not enabled at capture; whether a full scrub ever ran is unverified, and rarely read data has no recorded verification". The verdict should be `UNVERIFIED`, not `DEGRADED`.
11. SH5, "which fields (critical warning, available spare against its threshold, percentage used, media and data integrity errors) decide it".
    - [obs] Contradicted. The verdict is one byte: `(!w ? "PASSED" : "FAILED!")` (`nvmeprint.cpp:450-451`). The caller is `print_critical_warning(smart_log.critical_warning); if (smart_log.critical_warning) retval |= FAILSTATUS;` (`nvmeprint.cpp:840-842`). Spare, threshold, percentage used and media errors are only printed (`nvmeprint.cpp:501-511,530-531`).
    - [obs] The spare-against-threshold case enters only as controller-set bit 0x01, "available spare has fallen below threshold" (`nvmeprint.cpp:458-459`). [inf] When bit 0x04, "NVM subsystem reliability has been degraded" (`nvmeprint.cpp:464-465`), is set is up to the controller's firmware.
    - So SH5 needs no firmware-specific behaviour if it says "smartctl reports the controller's Critical Warning byte". It does need firmware-specific behaviour if it claims which media-error or wear levels set a bit.
    - The source seat reached the same result independently (`.ufo/waves/round-26/w1/SrcSmartNvmeprint.md:59-68`).
    - Correction: "smartctl 7.5 prints PASSED exactly when the Critical Warning byte is 0, and sets its FAILSTATUS exit bit otherwise; spare, percentage used and media errors are separate signals the operator reads against their own meanings; the conditions that set the reliability bit are controller-defined".
12. SH6, "cumulative over the device's life, not dated incidents".
    - [obs] Holds in substance. The specification says "over the life of the controller and is retained across power cycles unless otherwise specified" (`.ufo/waves/round-26/sources/S135.txt:21282-21283`, as reported in `SrcNvmeLifetimeFields.md:27`).
    - Wording limits: "controller", not "device", and "unless otherwise specified". "Unsafe Shutdowns" is renamed "Unexpected Power Losses" (`SrcNvmeLifetimeFields.md:29,40`).
    - [inf] 200 of 325 power cycles (`capture.txt:194,196`) counts power losses without a shutdown notification. It is not a crash count or a data-loss count, and the row's action must not say it is.
    - [obs] Two captured counters moved between the smartctl and nvme-cli queries, taken seconds apart. Data units read went from 166,723,542 to 166723544 (`capture.txt:189,216`), and host read commands from 3,519,217,605 to 3519217625 (`capture.txt:191,218`). Power cycles and unsafe shutdowns match (325/325 and 200/200). A row may only claim that the two tools agree for counters that did not move.
    - Correction: say "over the controller's life", and add "an increment can be dated only to the window between two captures".
