## Findings

### F1 — HIGH — `parse_limine_version` crashes (traceback) instead of rc 64 on over-long digit runs
- **File:line:** `tools/check-limine-pins.py:78-85`
- **Defect:** `tuple(int(p) for p in parts)` raises `ValueError: Exceeds the limit (4300 digits) for integer string conversion` on CPython ≥3.11 when a component has >4300 digits. `main()` (445-448) and `check()` (154-156) both call `parse_limine_version` *outside* any guard that maps that `ValueError` to usage rc 64 (`check()` itself re-raises a *different* `ValueError` for `None`, which `main()` never reaches because it pre-checks). Result: uncaught traceback, exit 1, no JSON, traceback on stderr — violates the docstring contract "anything else -> None (usage error, rc 64)" and the battery's `usage_check` usage contract.
- **Receipt:** `probe_gate.py` + CLI run: `python3 check-limine-pins.py --limine-version "$(python3 -c 'print("9"*5000)') .0.0"` → `ValueError` traceback at line 85 (reproduced in scratch). Normal short versions unaffected.
- **Counterexample:** `--limine-version 999…9 (5000 digits).0.0` → crash, should be rc 64.
- **One-line fix:** bound the digits before `int()`, e.g. `if len(parts) != 3 or not all(p.isascii() and p.isdigit() and len(p) <= 4 for p in parts): return None` (or try/except around `int()` → `None`).

### F2 — MEDIUM — leading-zero versions accepted (`12.09.4`, `1.2.03`, `00.00.00`); tested neither by gate selftest nor battery `usage_check`
- **File:line:** `tools/check-limine-pins.py:83` (`p.isdigit()` accepts `09`/`03`/`00`); `usage_check` cases at battery:2033 `[("12.9",64),("abc",64),("12.9.6.1",64),("",64),("12.9.4",0),("12.9.5",0),("13.0.0",0),(None,0)]`; gate selftest parser probe at gate:407-413.
- **Behavior:** `12.09.4` → `(12,9,4)` era A, CLI rc 1 (not 64). Semantically the version *means* 12.9.4, so era selection is not wrong; the issue is contract precision: C2 says "refuses versions outside X.Y.Z". `12.09.4` is inside the literal `X.Y.Z` pattern, so accepting is defensible, but *no* receipt pins this choice — `usage_check` never probes `12.09.4`/`1.2.03`/`00.00.00`, and the selftest never asserts them. A future "strict" reading (canonical `X.Y.Z` without leading zeros) would flip these from accept to rc 64 silently.
- **Counterexample:** `--limine-version 12.09.4` on the first-line-entry fixture → `prompt` (era A), rc 1; under a strict canonical reading → rc 64. Gate and battery agree today only because neither checks.
- **One-line fix:** decide and pin it in both places: either add `("12.09.4",0)` and `("00.00.00",0)` to `usage_check` (accepting, `int()` normalization), or reject in `parse_limine_version` (`p == "0" or not p.startswith("0")`) and add the same row with `want=64`. Docstring should state the choice (gate:79).

### F3 — MEDIUM — battery `--selftest` bypasses the `bwrap` guard; with no `bwrap` it crashes instead of reporting `could-not-evaluate`
- **File:line:** `tools/limine-pin-battery-r92.py:2066-2070` (`if a.selftest: return selftest(…) ` precedes `if not BWRAP: return 2`); `BWRAP = shutil.which("bwrap")` at 1744; `sandbox_argv` at 1747 returns `[None, …]` when absent; `run_gate` catches only `TimeoutExpired` (1783), so `subprocess.run([None,…])` raises uncaught `TypeError`.
- **Behavior:** `main()` battery/probe paths correctly refuse with exit 2 and "bwrap not found" — so **a `met` pass when `bwrap` is missing is impossible** (good). But `selftest` (the oracle-honesty self-check) skips that guard: without `bwrap` it traceback-crashes mid-`run_battery` instead of a clean exit. A crashed selftest writes no receipt, so it cannot lie — but an operator could mistake the traceback for a broken battery and rerun unguarded, or miss the `could-not-evaluate` signal.
- **One-line fix:** move the `if not BWRAP: … return 2` block above `if a.selftest:` (or duplicate the check inside `selftest` before any `run_battery`).

### F4 — LOW — gate selftest passes `tpm="1"` (string); `on_panic_of` truthiness makes `"0"` behave as `"1"`
- **File:line:** gate `selftest` `case("era-a-measured"…, tpm="1")` (403) / `case("era-b-measured"…, tpm="1")` (405); `on_panic_of` at 143-150 (`return "halt" if tpm else "menu"`, with `tpm is None` check first).
- **Behavior:** probed in-process: `check(..., tpm="1")` → `halt`, `check(..., tpm="0")` → `halt` (wrong; documented string contract is the CLI `"0"`/`"1"`, which `main()` converts to `bool` at 449, so the *battery* path is correct). The string case never reaches `on_panic_of` via CLI or battery; it only hits the selftest's two `tpm="1"` rows, which pass for the wrong reason (non-empty string is truthy). `tpm_present` in JSON is the raw string `"1"`, not a bool — inconsistent with the JSON the battery sees (`run_gate` uses `out.get("on_panic")` only, so no receipt impact).
- **One-line fix:** change the two selftest rows to `tpm=True` (or normalize in `check()`: `tpm = (tpm == "1") if isinstance(tpm, str) else tpm`).

### F5 — LOW — docstring drift: UsageParser comment says argparse rc 2 collides with CANNOT-EVALUATE rc 2, but the diff changed nothing there; `check()` docstring/`--live` help still says "Limine v12.9.4 path-pin gate" while V2 ships 12.9.5+ behavior
- **File:line:** gate:434 `UsageParser(description="Read-only Limine v12.9.4 path-pin gate.")`; diff hunks for docstring (1-41) correctly updated the rules text. `--live` path (450-456) passes the version through correctly (see "Verified correct" below) — only the description string is stale. Harmless; receipt text on stderr only. No fix required for C1/C2; update to "v12.9.4 and v12.9.5+" for consistency with the module docstring.

## Counterexamples (as tasked) — results

1. **Era A vs B with first line `/` + CR (`b"/\r\npath: …#bad\nhash_mismatch_panic: no\n"`).** Gate: era A (`12.9.4`) → `panic={line:3,value:no}`, `prompt`; era B (`12.9.6`) → `panic=None`, `panic`. **Matches upstream**: Limine strips every CR from the buffer before parsing (per R1/config.c), so a CR'd `/` line is still an entry line; v12.9.6 treats `p==config_addr` as the first entry and NULs the label end, leaving an empty global section in era B. No divergence; `probe_counterex.py` (`ce-cr`).
2. **Version `12.09.4`.** `parse_limine_version("12.09.4") == (12,9,4)` → era A on the first-line-entry fixture (`prompt`, CLI rc 1). **Accepted, not refused.** This is visible-but-untested contract surface (F2), not a wrong-era bug: `int("09")==9`, so the era answer is the 12.9.4 answer. The docstring says "anything else -> None", and a leading-zero string is arguably not "else". No receipt covers it either way.

## Residual risk / verification gaps

- Battery r92 was *not* executed end-to-end (356 sandboxed cases × runs would take minutes and is out of this seat's scope to burn); isolation was proven with a single live `bwrap` probe in an equivalent layout, and every code path was traced + probed in-process. **Verification gaps:** no `met`/`unmet` verdict re-derived here (that is the C1/C2 measurement seats' job); recommend the lane run `--selftest --reference` + `--isolation-check` + `--usage-check` + one `--runs 3` canonical/clone measurement and archive the JSON.
- `check()`'s `ValueError` on bad version (gate:155-156) is only triggered via library import; CLI always pre-checks. If any tool imports `check()` with an attacker string, F1 applies there too — the same fix covers both.
- `schema` bump `tsukuroi-limine-pins-v2 → v3` (gate:278) has no in-lane consumer reading the old string (grep: zero hits outside the bends); any out-of-lane consumer pinning `v2` will need the bump noted.
