## Findings — mutants that change the reported counts without failing loudly

Every mutant below exited 0, produced 34 stdout lines, an empty stderr, and a well-formed JSON summary line. None of them announces the change; only the numbers move.

5. [obs] **M9 — export step takes the counter blob from the base revision instead of `--counter-rev`** (`mutants-adjacency-overlap.py:55`, replacement `ARGS.counter_rev` → `rev`). Mutant sha256 `5e3bfe4fb10e3824ca96d4f625e232a36e82868d4a51eae64cd09dec195dec668`. At `--counter-rev f8e3a8f…` the run reports `should_fail_accepted` **19** instead of the declared 0, `control_live_anchored_rows` 6, exit 0, empty stderr. At `--counter-rev dd94cb1f` nothing changes, because the base `3b9e0430` and `dd94cb1f` carry byte-identical counter blobs (both sha256 `4d992f83f1868a61…`; command: `git show 3b9e0430:tools/check-adjacency-overlap.py | sha256sum` and `git show dd94cb1f:tools/check-adjacency-overlap.py | sha256sum`, both `4d992f83…`). [inf] This is the sharpest misreport path: the mutation reproduces the round-27 *before* value (19 of 24) under the round-28 counter revision, so an auditor reading only `should_fail_accepted` would conclude the B1–B7 tightening never landed. The mutation is not fully silent in the summary: the `counter_sha256` field drops to `4d992f83f1868a61…` while `counter_rev` still prints the requested `f8e3a8f…` (mismatched pair), so it is detectable only by cross-checking `counter_sha256` against `git show <rev>:tools/check-adjacency-overlap.py | sha256sum`.

Mutant sha256 `a67d98134ab829bd00d958546431cdfcb55547f0457915bd2566019c8268f641`. At `--counter-rev dd94cb1f` the run reports `should_fail_accepted` **0** instead of the declared before-value 19, exit 0, empty stderr; at `--counter-rev f8e3a8f…` the count stays 0 but `counter_sha256` changes. [obs] The bytes the worktree read are time-dependent: this run captured sha256 `f38da8eb1e77ce82…`, which is not any committed blob of the counter (a scan of the lane's blob objects returns only `4d992f83f1868a61…`, `450b020b0bae5e1f…` and `7b58652a7e9aaf85…`) — it was an uncommitted intermediate state of the lane worktree at that moment. [inf] A revision-unpinned counter source makes the counting command's verdict depend on which bytes happen to sit on disk, and it can silently report the opposite of the declared before-value.

## What this means for the declared values

22. [inf] The declared pair ("0 of 24 accepted, `control_live_anchored_rows` 6, exit 0" at the round-28 counter) is reproduced exactly by the pristine battery at `f8e3a8f…`, and the declared before-value ("19 of 24 at `dd94cb1f`") is reproduced exactly too. Neither number is robust to a defect in the battery: nine single-point mutations move one of those numbers while exiting 0 with an empty stderr, and three of them (M9, M12, M7) move the headline accepted count directly. [inf] The battery therefore has no internal consistency check that would make such a misreport loud — the receipt is the summary line, and the summary line is what the mutants move. A counter-reading defect that swaps the counter blob (M9, M12) is the most consequential, because it reproduces the previous round's number under the new revision; the `counter_sha256` field is the only thing in the output that discriminates it, and the declared counting command in the round-28 declaration names only `should_fail_accepted` and `control_live_anchored_rows`.
