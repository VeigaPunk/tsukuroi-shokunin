### 2.1 Lockdown word grammar (`mine-strict:lockdown-form`, 244/235)

Frozen: “lockdown is a string without exactly one whitespace-separated word of the form `[x]`” (battery docstring
41–42). The candidate selects any word with `len(w) > 2 and w[0] == "[" and w[-1] == "]"` (candidate 87, 96; it
requires exactly one such word). The cleanroom requires `\[[^\[\]]+\]`. The two disagree on words such as
`[none]]`, `[[none]`, `[[none]]`, `[a]]`, `[[a]`, `[a][b]`: the candidate accepts them as the selected word, the
cleanroom returns CANNOT-EVALUATE. The frozen text does not define the grammar of `x`; the kernel can only emit
exactly one of `none`, `integrity`, `confidentiality` in brackets (security/lockdown/lockdown.c 20–22, 96–118),
so every disputed form is outside the capture domain. Neither side contradicts the text. Noted as a margin and a
small risk (§4 R2), not a predicate defect: the candidate turns a malformed document into an evaluation where a
strict reading would refuse, e.g. `[[integrity]]` selects the non-blocking mode `[integrity]` and reads HEALTHY.

### 2.2 `resume_offset=` token grammar (`offset-syntax`, 150/136)

Frozen: `o` is “the value of the last `resume_offset=` token or None” (battery docstring 13–14) and rc 2 is
enumerated only for schema, missing/wrong-typed required keys, and lockdown format (39–42); rules 1–8 then use
`o` as an integer (26–37). The candidate takes
the last token and does `int(raw_o)`, raising `Malformed("resume_offset-not-int")` → rc 2 on any non-integer
(candidate 138–142). The cleanroom parses only `[0-9]+` and otherwise ignores the token (kernel-style), so with
`resume_offset=abc` the candidate refuses while the cleanroom reports e.g. HR-OFFSET-MISSING, and with
`resume_offset=+3795013` the candidate evaluates `3795013` while the cleanroom treats it as absent. Examples:
`T9:...resume_offset=abc` → cleanroom `1 DEGRADED [HR-OFFSET-MISSING]`, candidate `2 CANNOT-EVALUATE`; `T9:...resume_offset=+3795013` → cleanroom `1 DEGRADED [HR-OFFSET-MISSING]`, candidate `0 HEALTHY`. A whole-token
integer is a defensible reading of “the value”; the rc 2 is an extension beyond the enumerated rc-2 list, and the
cleanroom's silent ignore is an extension in the other direction. Under-specified; the candidate refuses
non-integers (`abc`, `0x10`, `3795013x`) but accepts the signed forms `+n`/`-n` that the kernel's `%llu`
converter ignores, so it can answer HEALTHY on a token the kernel never applies. Kernel semantics differ from both
(see 3.5).

### 2.3 `sys_power_resume.strip()` (`strip:sys_power_resume`, 81/89)

Frozen rule 3 compares `resume_dev_majmin` with `sys_power_resume` (battery docstring 32). The candidate compares
`f["sys_power_resume"].strip()` (candidate 152; the same line as the candidate-free round-84 control K2,
`before/controls/k2-schema-shim.py:104`). On padded values (`"253:0\n"`, `" 253:0"`) the candidate reports no
HR-SYSFS-DEVICE-MISMATCH where the cleanroom reports one, e.g. `R25` → cleanroom `1 DEGRADED
[HR-HIBERNATE-DISABLED, HR-SYSFS-DEVICE-MISMATCH]`, candidate `1 DEGRADED [HR-HIBERNATE-DISABLED]`. The capture
tool itself strips the sysfs read (`tools/capture-resume-facts-r84.py:89`), so documents produced by the intended
path never carry padding: no frozen-domain case exists. The candidate's normalization is semantically sensible
(device numbers, not bytes); the literal rule text says nothing about stripping. Under-specified margin; the
frozen text should say `strip` if the normalization is intended (Limits).

### 2.4 Nullable chain fields (`cand-strict:*`, 63/71)

The candidate requires `sys_power_resume` to be a non-null string and `sys_power_resume_offset` a non-null
integer (`need` calls in its `validate`, lines 52–86). The cleanroom allowed `null` for both. The frozen text

### 2.5 Swap-entry shape (`mine-strict:swaps-path/type`, 2/2)

The cleanroom required each `swaps[]` entry to carry `path` and `type` strings; the candidate (and the round-84

candidate (HR-SWAP-TOO-SMALL) and refused by the cleanroom. **The cleanroom is wrong** (extra strictness).

### 3.1 Bare `nohibernate`/`noresume` tokens: equality vs the kernel’s `__setup` prefix matcher

Frozen A1/A3 fire on “a token equal to `nohibernate`” / “a token equal to `noresume`” (battery docstring 19, 23).
The kernel registers `__setup("noresume", noresume_setup);` (kernel/power/hibernate.c 1518) and
`__setup("nohibernate", nohibernate_setup);` (1524). The kernel's obsolete-parameter matcher compares only the
first `strlen(p->str)` bytes and calls the handler with the remainder, with **no delimiter requirement** for
non-early entries:

```text
init/main.c:201  static bool __init obsolete_checksetup(char *line)
init/main.c:209      if (parameqn(line, p->str, n)) {
init/main.c:221      } else if (p->setup_func(line + n))
                       return true;
init/main.c:463  static void __init repair_env_string(char *param, char *val)   /* restores '=' into param */
init/main.c:518      repair_env_string(param, val);                            /* before obsolete_checksetup */
init/main.c:527      if (obsolete_checksetup(param))
```

(`parameqn` compares the first *n* name characters — include/linux/moduleparam.h 404–415 in the host's
`/lib/modules/7.2.11-arch1-1/build` tree; `repair_env_string` reestablishes `name=value` before the match.) Therefore, in the v7.2 kernel, **`noresumeX`, `noresume=1`,
`nohibernateX` and `nohibernate=1` all set the flags**, while the frozen rules (and both gates) report HEALTHY.
Measured, same host base, one token inserted:

```text
nohibernateX      cleanroom=0 HEALTHY []                      candidate=0 HEALTHY []
nohibernate=1     cleanroom=0 HEALTHY []                      candidate=0 HEALTHY []
noresumeX         cleanroom=0 HEALTHY []                      candidate=0 HEALTHY []
noresume=1        cleanroom=0 HEALTHY []                      candidate=0 HEALTHY []
```

Module-prefixed forms in PREC-DECOYS (`<mod>.noresume=1`, `<mod>.nohibernate=1`) stay decoys in the kernel too:
they do not start with the setup string and fall through to the unused-module-parameter path (init/main.c 530–532).
This is the largest text-vs-kernel gap: the rule text captures the `hibernate=` *value* prefix logic but models the
bare switches as exact words, which the kernel does not. A facts document from any source other than the pinned
host could therefore understate a real hibernation block.

### 3.2 `hibernate=` value prefixes — consistent

`hibernate_setup` (hibernate.c 1424–1438) tests `noresume` (1426), then `nocompress` (1428), then `no` (1430–1432,
setting **both** `noresume` and `nohibernate`), then `protect_image` (1433–1435). Frozen A1 excludes exactly
`noresume`/`nocompress` before the `no` test and A3 catches `noresume`, with A1 suppressing A3 — matching output.
Measured and agreeing: `hibernate=nope` → HIBERNATE-DISABLED only; `hibernate=noresumeX` → NORESUME-ARG;
`hibernate=nocompressX` → HEALTHY; `hibernate=protect_image` → HEALTHY; `hibernate=` → HEALTHY;
`hibernate=NO` → HEALTHY (case-sensitive). No divergence.

### 3.3 `noresume` is not part of `hibernation_available()` — terminology scoping

`hibernation_available()` is `nohibernate == 0 && !security_locked_down(LOCKDOWN_HIBERNATION) &&
!secretmem_active() && !cxl_mem_active()` (hibernate.c 109–113). `noresume` does not appear there; it only bails
`software_resume_initcall` (`if (noresume || !hibernation_available())`, hibernate.c 1106–1112). A3 nevertheless
groups `noresume` with the availability rules and emits HR-NORESUME-ARG. This is a declared-rule choice, not a
contradiction, but an operator must not read HR-NORESUME-ARG as “hibernation unavailable”: the kernel can still
hibernate, it just will not resume on boot.

### 3.4 Missing kernel blockers: `secretmem_active()` and `cxl_mem_active()`

hibernate.c 112–113 requires both to be false. `resume-facts/2` has no field for either, and A1–A3 have no rule
for them; a host where `secretmem_active()` or `cxl_mem_active()` is true would have `hibernation_available() ==
false` while the gate can report HEALTHY. This is a coverage Limit of the frozen schema, not a predicate change.
(The host in `before/host` shows no such evidence either way; the facts document cannot express it.)

### 3.5 `resume_offset=` parsing — the kernel is neither the candidate nor the cleanroom

`resume_offset_setup` uses `sscanf(str, "%llu", &offset)` and assigns only when the call returns 1 (hibernate.c
1411–1422, parse at 1418). The kernel's own vsscanf is not libc: lib/vsprintf.c v7.2 (fresh fetch, sha256
`cabb648a2c72fcbd4a1b00cbbf442ad11235f3224071f5e662db4a77993469ca`, `receipts/upstream/vsprintf.c`) sets
`base = 10`, `is_sign = false` for `%llu` (3548–3549, 3644–3645), skips leading spaces (3659), requires the first
character to be a decimal digit (`base == 10 && !isdigit(digit)` → break, 3669–3674) and converts with
`simple_strtoull` (3680–3681), whose radix fixup leaves base 10 unchanged (lib/kstrtox.c 26–40, fresh fetch
sha256 `0c52ae02259f06adaf0a72a572e31ede4d8d6519e1b5625cb6b18d74db8d1ee4`, `receipts/upstream/kstrtox.c`) and
parses a base-10 prefix (58–78). Therefore:

```text
kernel vsscanf("%llu"):  3795013 -> 3795013 ; 0123 -> 123 ; 3795013x -> 3795013 ; 3_795_013 -> 3 ;
                         0x10 -> 0 (base fixed at 10, stops at 'x') ; " 3795013" -> 3795013 ;
                         abc, +3795013, -1, empty -> no conversion, token ignored
```

The candidate's `int()` (candidate 138–142) accepts `-1` and `+3795013` where the kernel ignores the token, and
rejects `0x10`, `3_795_013`, `3795013x` and `abc` with rc 2 where the kernel would take 0, 3, 3795013 and ignore
respectively. The cleanroom's `[0-9]+` ignores all non-digit-only forms, matching the kernel for `abc`/`+n`/`-1`
but not for `3795013x`/`3_795_013`/`0x10`. Frozen rule text says only “the value of the last token” (13–14); it
states no grammar. Also, the kernel ignores `resume=` and `resume_offset=` if `noresume` was parsed earlier on the
command line (hibernate.c 1404–1405, 1415–1416): cmdline order matters in the kernel, while the rules take the
last token value regardless of order. Observed only at the margins (150/136 disagreements), never a battery case.

### 3.6 Lockdown — consistent, with a host row

`hibernation_available()` blocks when `security_locked_down(LOCKDOWN_HIBERNATION)` is non-zero (hibernate.c
111–112); `lockdown_is_locked_down` returns `-EPERM` when `kernel_locked_down >= what` (security/lockdown/
lockdown.c 65), and the levels are `LOCKDOWN_NONE < … < LOCKDOWN_HIBERNATION (5) < … < LOCKDOWN_INTEGRITY_MAX <
… < LOCKDOWN_CONFIDENTIALITY_MAX` (include/linux/security.h 128–149, `LOCKDOWN_HIBERNATION` at 133,
`LOCKDOWN_INTEGRITY_MAX` at 149). The sysfs file prints exactly one bracketed level out of `{none, integrity,
confidentiality}` (lockdown.c 20–22, 43–46, 96–118). Frozen A2 (“bracketed word is `integrity` or
`confidentiality`”) matches the kernel exactly; host `[none] integrity confidentiality` → no block, correctly.
No divergence. `hibernate=protect_image` (hibernate.c 1433–1435) hardens the restored image and is correctly not
a rule.

## 4. Risks and limits carried forward

- R1 (kernel gap, largest): bare `noresume=…`, `noresumeX`, `nohibernate=…`, `nohibernateX` disable
  hibernation/resume in the kernel but are HEALTHY under the frozen rules and both gates (§3.1). If the gate is
  used beyond this host's captured facts, this can understate a real block. A future declaration should decide
  whether A1/A3 adopt `__setup` prefix matching; I did not change the frozen rules.
- R2 (candidate leniency): exotic bracket words (`[[none]]`, `[a]]`, `[a][b]`) are accepted by the candidate as
  the lockdown selection (§2.1). Not reachable from the capture path; harmless for this battery, but a nested
  `[[integrity]]` reads non-blocking instead of CANNOT-EVALUATE.
- R3 (candidate literal-text deviations): `.strip()` in rule 3 and rc 2 for non-integer `resume_offset=` values
  are normalizations/fail-closed choices the frozen text does not spell out (§2.2–2.3); both are defensive, and
  neither changes any frozen-battery case.
- R4 (schema coverage): `secretmem_active()` / `cxl_mem_active()` are invisible to `resume-facts/2` (§3.4);
  `noresume` is a resume-path block, not a `hibernation_available()` condition (§3.3).
- R5 (method): the fuzz corpus is machine-generated and the cause labels are heuristic (single decisive
  anomaly; two rows combine two). The authoritative record is the raw document and both outputs in
  `receipts/fuzz-disagreements-classified.json`. Two seeds were run; both produced only the six classes above,
  zero unclassified cases.
- No blockers; every assigned step was run. Tooling: none installed or upgraded (no channel used). Scratch
  `/fast/scratch/hyaku/tsukuroi-r85/ExecCleanRoom` was removed after receipts were copied.
