VERDICT: defect-found

GR1's enumerated values are accurate, but its examples omit two operator-relevant behaviors: integer overflow without a suffix is silently accepted and clamped to `ULLONG_MAX`, and a zero-byte write is a no-op while a newline-only write clears the limit. I recommend extending the row so operators do not mistake a successful write for a parsed intended value or assume an empty write cleared the setting.

## Exact suggested replacement

Replace GR1's final two sentences (currently lines 22–25) with:

> The sysfs store then skips trailing whitespace and returns `-EINVAL` unless the text ends at the buffer's NUL terminator. Thus `100M` and `100m` both set 104857600 bytes per second, `010` sets 8, and `0x10` sets 16; `10MB` (a second letter), `10 M` (a blank before the suffix), and `-1` are rejected with `EINVAL`. A bare newline parses as 0 and is accepted, which removes the limit (0 means no limit, SR8); a zero-byte write is different: sysfs returns success without calling the store, so it leaves the previous limit unchanged. Also, `simple_strtoull` masks its parser's overflow flag: a decimal value above `ULLONG_MAX` without any suffix is accepted as `ULLONG_MAX`, not rejected. For example, `18446744073709551616` is accepted as `18446744073709551615`; do not treat a successful write of an out-of-range value as a validation error.

This preserves the existing examples, clarifies the NUL-termination premise with a source-backed term, and adds the two most operator-relevant omitted cases.
