## Findings

### High — GR1's “substantial” quote and token gates admit content-free evidence

`quote_good()` explicitly permits a quote equal to the stripped source line, regardless of length (`tools/check-scrub-grounding-r45.py:294-301`); `q_ok` then requires valid quotes, a window quote, and the required file keys (`:357`). All three GR1 required files also have a one-character `{` line inside a GR1 window: S246 `cmdline.c:154`, S246 `kstrtox.c:27`, and S243 `sysfs.c:2034` (the frozen snapshots named at `:88-104`; GR1 keys/windows at `:106-110`). The probe calls against those actual snapshot lines returned `quote_good=True` and `in_window=True` for each (`.ufo/waves/round-45/a2w1/C2RevCounter/probe-summary.txt`). Thus three quotes consisting only of `{` satisfy GR1's required-file and window checks.

The statement check is only substring presence (`:358-359`): `memparse simple_strtoull octal 1024 ULLONG_MAX EINVAL` passes all GR1 proposition checks without asserting any relationship. Likewise, the host check accepts only `capture.txt:1`, a non-empty generic capture-metadata line, as sufficient (`:126`, `:360-362`; capture source line 1 is `.../frozen/hostcap/capture.txt:1`). The same probe confirms this input passes `prop_ok` and `host_ok` (`probe-summary.txt`). A row with those quotes, tokens, and host reference passes all three automated GR1 content legs while grounding none of the asserted behavior. The actual implementation entry is not using this evasion: its 31 quote strings are all at least 10 characters, all statement tokens are present, and all cited capture lines are non-empty (receipt above). However, this contradicts the docstring's claim that the quote rule “closes the round-44 gutted-quote gap” (`:20-24`) and leaves a mechanically passable hollow row. The overall predicate still requires counted verdict bindings (`:65-66`); this finding concerns the content gates, not a claim that the current mid-wave revision already passes overall.

### Medium — Registry fence toggling misclassifies valid nested fence lengths

`registry()` toggles a boolean for every line beginning with either three backticks or three tildes, without remembering the opener character or run length (`tools/check-scrub-grounding-r45.py:186-204`). In CommonMark, a four-backtick fence may contain a triple-backtick example without closing the outer fence. A synthetic `## Registry` with an outer four-backtick fence, an inner triple-backtick fence, and a single 11-cell S246 row inside produced `rows=['S246']`, `dups=[]` (`.ufo/waves/round-45/a2w1/C2RevCounter/probe-summary.txt`). That row is therefore treated as live registry evidence despite being inside a fenced block, contrary to the documented scope rule (`:51-53`). This can falsely supply a required registry row if its real row is absent; duplicate detection does not help when there is only this one row-shaped occurrence.

### Low — Entry section parsing also treats fenced examples as live structure

`sections()` recognizes headings without tracking Markdown fences, and `block()` toggles on any unindented line beginning `**` (`tools/check-scrub-grounding-r45.py:160-184`). A synthetic fenced `## GR1` heading opened a GR1 section; duplicate `## GR1` headings silently merge (`probe-summary.txt`). Consequently, a fenced example containing row headings, quote lines, or statement/host labels can contribute to the live row checks, and malformed quote lines in such an example can also fail a row. This parser does not enforce the section/block structure that the docstring describes (`:10-19`).
