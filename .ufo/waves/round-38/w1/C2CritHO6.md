# C2CritHO6 — attack on HO6 and its boot consequence (item C2-11)

Claim under test, `corpus/knowledge/pacman-hook-order-r38.md:26` (freeze
`7cbaeb6317cb9f7323d2619eec02db4e4da29449`), verbatim:

> HO6 | PostTransaction hooks run only after `transaction completed`; a failed or interrupted commit runs none, and a
> Post hook's failure is ignored | S210 `trans.c:212-240` | A failed upgrade leaves the 52 Post hooks unrun, including
> `90-mkinitcpio-install.hook` (UKI rebuild) and `99-limine.hook`: after a failed transaction the boot artefacts were not
> regenerated by pacman

Short answer to the assigned question — **yes, the dangerous state exists**: `libalpm` commits targets one at a time and
records each in the local database before the next, keeps no rollback path, and gates the whole Post phase on
`state != STATE_INTERRUPTED` and on `_alpm_sync_commit() != -1`. A failure or an interrupt after the `linux` package has
been committed leaves the new modules tree installed with the previous UKI still on the ESP, and runs none of the 52
Post hooks. Two reachable paths, one of which returns **0** from `alpm_trans_commit`.

No clause of the rule *statement* is false. The defect is in the host-consequence cell and in its citation: the
partial-commit premise is not in `trans.c:212-240` and is not in the frozen source set at all, the consequence type is
version skew rather than "not regenerated", and the interrupt path is reported as success.

## Finding 1 — the three clauses hold, with their exact mechanics

`trans.c:232-239` is the `else` of `if(trans->state == STATE_INTERRUPTED)`; line 235 logs `transaction completed` and
line 238 runs the Post phase. A failed commit never reaches it: `trans.c:220-227` returns `-1` right after logging
`transaction failed`. The Post return value is discarded at `trans.c:238`, and `hook.c:660-668` can only set the abort
flag inside a Pre run, while `hook.c:141-146` rejects `AbortOnFail` on a Post hook at load — so `_alpm_hook_run(…POST…)`
returns 0 unconditionally. Clause 3 therefore holds twice over.

Precision the row should keep: "ignored" means *not propagated*, not *not logged*. `_alpm_run_chroot` logs
`command failed to execute correctly` at ERROR (`util.c:789`), and the frontend's `cb_log` writes that only to stderr
(`callback.c:1139-1154`; `ALPM_EVENT_HOOK_RUN_DONE` is a `/* nothing */` case, `callback.c:416-418`). Nothing durable
about a failed Post hook reaches `pacman.log`; only `transaction failed` / `transaction interrupted` do.

## Finding 2 — the dangerous state is reachable, in two paths

Commit is per-target, not atomic (`add.c:670-687`): `commit_single_pkg` extracts the archive (`add.c:541-561`), then
writes the local DB entry (`add.c:599-607`), then logs the upgrade and runs the package scriptlet (`add.c:618-647`,
whose return value is not checked), then returns. `grep "rollback\|revert\|undo\|_alpm_handle_commit_error" add.c`
returns nothing (`receipts.txt`, rc=1): **there is no rollback**. `sync.c:1336-1360` calls it and returns `-1` on the
first failing target.

- Path A (error): `add.c:677-684` sets `trans->state = STATE_INTERRUPTED`, `ret = -1`; the next loop head returns
  (`add.c:673-674`); `sync.c:1354-1357` returns `-1`; `trans.c:220-227` logs `transaction failed` and returns `-1`.
  Post hooks skipped.
- Path B (interrupt): `alpm_trans_interrupt` sets `STATE_INTERRUPTED` (`trans.c:252-261`); the loop head returns `ret`,
  which is **0** when no earlier target failed (`add.c:673-674`); `sync.c:1354` is false; `trans.c:230-232` logs
  `transaction interrupted` and execution falls to `trans.c:242-244`, which returns **0**.

In both paths every target committed before the failing or in-flight one stays installed, including `linux`, and no
Post hook runs.

Host instance, quantified (`receipts.txt`): the 2026-10-20 `-Syu` ran `transaction started` at `pacman.log:2479` and
`transaction completed` at `pacman.log:2941` with **448** commit lines; `upgraded linux (7.2.3.arch1-3 -> 7.2.11.arch1-1)`
is at `pacman.log:2855`, and **83** targets commit after it but before completion. Every one of those 83 was a window in
which a failure would have left `/usr/lib/modules/7.2.11-arch1-1` in place, the UKI still carrying 7.2.3 and its
initramfs, and all 52 Post hooks unrun — including `nvidia-open-dkms` 610.57.04→615.78.08, which commits *inside* that
window (`pacman.log:2892`). `dkms` build failures are routine, so the window is not hypothetical in kind.

## Finding 3 — the interrupt path is a success return, not a failure

This is the part HO6's "failed or interrupted" phrasing hides. `pacman`'s handler calls the API on SIGINT/SIGHUP
(`sighandler.c:52-73`, `:76-89`), the library sets `STATE_INTERRUPTED`, and `alpm_trans_commit` then returns 0
(`trans.c:242-244`). The frontend only treats `-1` as failure (`src/pacman/sync.c:848`), so pacman exits 0 with the
UKI not rebuilt. A scripted flow (`omarchy-update`, `pacman -Syu || exit 1`) sees success; the only automated witness is
the string `transaction interrupted` at `trans.c:231`. Also note the granularity: the in-flight package completes
(its extraction loop does not test the state, `add.c:541-561`), so an interrupt commits whole packages, not half of one.
Strongest form: a SIGINT that arrives after the *last* target commits is still seen at `trans.c:230`, so a transaction in
which **every** package was extracted and DB-recorded — kernel included — runs none of the 52 Post hooks and returns 0.

## Finding 4 — the consequence is skew, not deletion; and it is conditioned on what the Pre phase did

Post hooks rebuild; Pre hooks *remove*, and they run before any target (`trans.c:201-204`). `60-mkinitcpio-remove.hook`
(PreTransaction, Path Remove `usr/lib/modules/*/vmlinuz`, digest equal to the capture MANIFEST) runs
`mkinitcpio remove`, whose `rm -f` list is the preset-derived or fallback set `/boot/vmlinuz-<pkgbase>`,
`/boot/initramfs-<pkgbase>{,-fallback}.img`, `/efi/EFI/Linux/arch-<pkgbase>{,-fallback}.efi`
(`/usr/share/libalpm/scripts/mkinitcpio:118-124`, `:159-178`, `:279`).

On this host that list does not contain the boot artefact: `/etc/mkinitcpio.d` is empty (`ls -A | wc -l` = 0), `linux`
owns only `usr/lib/modules/7.2.11-arch1-1/vmlinuz` (`/var/lib/pacman/local/linux-7.2.11.arch1-1/files:7750`), and the UKI
is `/boot/EFI/Linux/omarchy_linux.efi` (`ESP_PATH="/boot"`, `ENABLE_UKI=yes`, `CUSTOM_UKI_NAME="omarchy"` —
`/etc/default/limine:3,8,9`; path form at `limine-mkinitcpio-install:143`). So the UKI survives a failed transaction:
the exposure is **stale kernel + initramfs under a new modules tree**, not a missing image. The mirror case is the one to
record: had a preset set `ALL_uki` to the UKI path, the same Pre hook would delete it before extraction and the same
failure would leave the machine with no kernel image for that entry, i.e. a different class of harm.

The Pre phase did commit its own side effect: `60-limine-mkinitcpio-remove-pre.hook` appends the pkgbase to
`/var/lib/limine/removed_kernels.list` (`limine-mkinitcpio-remove:15-33`, append at `:31`), a file whose header says it
"persists in case of an kernel upgrade failure or power outage" (`:6-7`). The Post hook is what clears it (`limine-mkinitcpio-install:324-327`),
so a failed transaction leaves both the skew and this residue. `/var/lib/limine` is empty now (`ls -A`), consistent with
60/60 completed transactions and no failure ever.

There is no automatic repair: no unit rebuilds boot UKIs. `limine-snapper-sync.service` runs `limine-snapper-watcher`;
the only other units mentioning mkinitcpio are `mkinitcpio-generate-shutdown-ramfs.service` (builds a *shutdown* ramfs
into `/run/initramfs`, `-k none`) and `plymouth-switch-root-initramfs.service`. The recovery path is the operator
`limine-update` already named at `boot-chain-r17.md:25-26` and `pacman-hook-order-r38.md:106-107`.

Silent-success variant worth naming: even when the Post hook *does* run, `limine-mkinitcpio-install` exits 0 on a failed
build — `process_uki_kernel || return 0` (`:296-300`), `process_kernel "$kernel_dir" || true` (`:315`), with only
`error_msg "mkinitcpio failed … skipping."` (`:230`, `:259`, `:272`) on stderr, which libalpm relays as an
`ALPM-SCRIPTLET` line. So "a Post hook's failure is ignored" understates the case: there may be no failing exit status
to ignore.

## Finding 6 — `99-limine.hook` is the wrong second example

Its trigger is `Operation = Install/Upgrade`, `Type = Package`, `Target = limine` (`/etc/pacman.d/hooks/99-limine.hook:1-5`);
its action copies `BOOTIA32.EFI`/`BOOTX64.EFI` into `/boot/EFI/BOOT/` (`:7-10`). It produces the limine *bootloader*
binaries, not a kernel entry, and it is not in the transaction at all unless `limine` is a target. It is also owned by no
installed package: `grep -l "99-limine.hook" /var/lib/pacman/local/*/files` returns nothing (the same for
`walker-restart.hook`), which resolves `boot-writers-r19.md`'s [unk] "owner of `99-limine.hook`" — nobody owns it, it is a
local file. `90-mkinitcpio-install.hook`, by contrast, is owned (`limine-mkinitcpio-hook-1.40.0-2/files:14-15`).
