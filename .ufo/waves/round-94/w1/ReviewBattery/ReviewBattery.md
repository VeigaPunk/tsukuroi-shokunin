Trace is to the gate's own V2 clause, not to a Limine source line: the 9-digit cap is the gate's own anti-`int()` guard (gate line 94-95: `int()` raises above 4300 digits), not a Limine upstream fact. That is fine for a gate contract, but it is not a Limine-source-traced rule; the claim text does not pretend otherwise.
- **AUTO-PROBE-SHAPES** certifies the probe-failure contract for two shapes: (a) stdout with no parsable version (`no version here`) and (b) a suffixed pre-release answer (`Limine 12.9.6-rc1`), both exit 0, plus a stderr copy `Limine 12.9.6` that must never be read (battery line 1700; fake materialised battery lines 1911-1916). ## 3. Vacuity check: AUTO-ERA-B vs the `shapes` fake's `12.9.6-rc1` line

- The `shapes` fake (battery 1916) prints, on stdout in order: `no version here`, `Limine 12.9.6-rc1`, and on stderr `Limine 12.9.6`. The probe reads stdout only and takes the first match. With the suffix guard deleted (`(?![\w.-])` removed), the regex matches `12.9.6` inside `12.9.6-rc1` and the gate resolves 12.9.6 → era B verdict instead of refusing.
- `AUTO-ERA-B` uses a **separate** fake that prints exactly `Limine 12.9.6` (battery line 1918, `echo "Limine %s"` with `c.auto = "12.9.6"`), NOT the `shapes` script. The `-rc1` line therefore cannot leak into AUTO-ERA-B's expectation. However the converse direction matters for vacuity: does a lenient gate pass AUTO-ERA-B vacuously? Yes, in one sense — a gate that reads the probe but never checks the suffix agrees with the expectation on AUTO-ERA-B (correct 12.9.6, correct era-B `panic`). AUTO-ERA-B alone does not certify suffix strictness; that power lives entirely in AUTO-PROBE-SHAPES, exactly as designed (family names this split in docstrings: battery lines 1700-1706, 1727-1730). Not a defect — the pair is the intended design.

## 4. Findings

**F1 — AUTO-PROBE-SHAPES does not certify the `12.9.6.1` (extra-component) shape.** The battery rule text (battery line 145) and gate regex (gate line 121 `(?![\w.-])`) certify two suffixed shapes — `-rc1` and `.1` — but the battery `shapes` fake sends only `-rc1` (battery line 1916). A bend that keeps the hyphen case blocked but admits `.1` (e.g. guard `(?![\w])` instead of `(?![\w.-])`, which still blocks `-` but also blocks `.`... in fact `(?![\w.-])` vs `(?![\w])`: the latter blocks `6.1` since `.` is not `\w`, so `(?![\w])` blocks both too; the realistic discriminator is a guard that only blocks `-` — e.g. `(?![\w-])` — which admits `12.9.6.1`) would pass AUTO-PROBE-SHAPES and every other family while violating battery line 145's stated contract. Counterexample: guard `(?![\w-])` on the `shapes` fake → no regex match (`-` still blocked) → rc 64 → family passes; same gate on `Limine 12.9.6.1` → matches `12.9.6` → verdict → rule text falsified at battery line 145 / gate line 48. Falsified line: battery line 145 (`a suffixed/extra-component answer) is a usage error`) — the certified enumeration covers only half the stated disjunction. Severity: low (the guard is one regex; full battery coverage would need a second fake body or a second case; the gate's own selftest at gate line 474 does exercise `.1`, but the battery does not).

**F2 — REFUSAL-VERSIONS-10DIGIT has no lower-bound (accepted-side) control for the 9-digit boundary; an over-strict gate scores `met`.** Counterexample: `gate-strict8.py` (`len(p) <= 8`) returned battery verdict `met` 98/98 with 0 error rows — it refuses exactly-9-digit components that the published rule accepts (gate `parse_limine_version("999999999.9.9")` → `(999999999, 9, 9)` on the landed gate; docstring gate lines 92-93 accept 1-9 digits, and `REFUSAL_DIGIT9` at battery line 1684 exists precisely as that accepted boundary member). The family docstring (battery lines 1691-1692) explicitly disclaims this: `Accepted boundary: 999,999,999 (9 digits) reads a verdict (that case belongs to the gate's selftest, not this finite enumeration).` The disclaimed case is not exercised at battery level; the gate selftest checks `parse_limine_version("9" * 5000 + ".0.0") is None` (gate line 452) but no battery family ever submits a 9-digit value as an accepted version. So the accepted side of the 9-digit cap is uncertified by the battery: a gate bent the other way (`<= 8`) passes everything. Falsified line: battery line 1684 `REFUSAL_DIGIT9 = "9" * 9 + ".9.9"  # ... ACCEPTED` — the constant is declared but never sent to any gate through the battery (only the landed gate's selftest path uses the cap's upper end). Severity: medium-low (declared and documented as out of scope at battery line 1691-1692; the failure is honest — it is a stated residual, not a hidden gap — but it means C1's `the 9-digit component cap` certification is one-sided: refusal side certified, acceptance side not).

**No F3 — enumeration and rule-trace findings:** position coverage complete (Q2: no missed position); both families trace to the cited rule text lines (gate 91-101, 107-122; battery 139-146) and a literal-ruled gate passes both (Q1). AUTO-ERA-B vacuity: the `-rc1` line belongs to a different fake than AUTO-ERA-B's, and the lenient-overfit direction (suffix guard removed or stderr read) is killed by AUTO-PROBE-SHAPES at 97/98 with exactly one failed family — no bend defeats a family that should kill it, except the two narrower gaps above.
