## Part 2 — Pre-source mechanism assumptions (QUALITY 63) against Linux v7.2

All sources below were fetched with plain curl, pinned to tag v7.2. My copies are in /fast/scratch/hyaku/tsuku27/CritLearningFrontier/src/. The lane snapshots S140 to S145 in .ufo/waves/round-27/sources/ are byte-identical to my fetches (`cmp` returned 0 for all six).

5. [obs] Each declared question (SCORECARD.md:998) checked against the sources:
   - **KT1 is narrowed.** The name "unsigned-module flag" is pre-source. https://raw.githubusercontent.com/torvalds/linux/v7.2/Documentation/admin-guide/tainted-kernels.rst line 98 labels bit 13 "unsigned module was loaded". However, kernel/module/signing.c lines 106-107 also clear `sig_ok` for a signed module whose key is unavailable: "case -ENOKEY: reason = \"module with unavailable key\";". So decoding 12288 as "an unsigned module" is wrong for this host. Bits 12 and 13 (4096 + 8192 = 12288) are confirmed by include/linux/panic.h lines 83-84.
   - **KT2 holds, with one refinement.** v7.2 sets O when the module's modinfo lacks `intree`, not because of where the module file sits: kernel/module/main.c line 2575 reads "if (!get_modinfo(info, \"intree\")) {". The message is printed only when O is not already set (main.c line 2576, `if (!test_taint(TAINT_OOT_MODULE))`). That explains why the capture has a journal line for nvidia only (capture.txt:136) while four modules carry O.
   - **KT3 is contradicted in its framing and narrowed in mechanism.**
     - The E message is not in signing.c. It is in kernel/module/main.c lines 2606-2610 and is printed with `pr_notice_once`, so it appears once per boot no matter how many modules fail.
     - signing.c decides `sig_ok`. A module that loaded with E must have hit -ENODATA, -ENOPKG or -ENOKEY (signing.c lines 99-108). Every other error is fatal "even if signatures aren't required" (lines 111-116). So a named signer plus a successful load plus E means "key unavailable" or "unsupported crypto". CONFIG_CRYPTO_RSA=y on this host (`zgrep` of /proc/config.gz, exit 0), which leaves -ENOKEY as the remaining explanation [inf].
     - Verification uses `VERIFY_USE_SECONDARY_KEYRING` (signing.c line 65). In certs/system_keyring.c that keyring links .builtin_trusted_keys (lines 253-254) and .machine (lines 187-192), but not .platform, which is where UEFI db certificates go (security/integrity/platform_certs/keyring_handler.c lines 50-53, `add_to_platform_keyring`).
     - Host evidence from read-only `journalctl -k -b 0 --no-pager -o short-monotonic | grep -iE 'X\.509|keyring|MOK|secureboot|secure boot|lockdown|integrity'` (exit 0). It shows "Secure boot disabled" at 17.513318, exactly one compiled-in certificate ("Build time autogenerated kernel key: 6961…"), six UEFI:db certificates loaded via "integrity:" (the platform keyring), and no MokListRT line.
   - **KT3's operator action is contradicted for this host.** security/integrity/platform_certs/load_uefi.c line 214 reads "the MOK/MOKx can not be trusted when secure boot is disabled", and line 216 returns before `load_moklist_certs()`. Even with Secure Boot on, a MOK certificate reaches .machine only when `imputed_trust_enabled()` is true (keyring_handler.c lines 64-66). On EFI systems that needs the MokListTrustedRT variable (machine_keyring.c lines 47-60, "If it does not exist, MOK keys should not be trusted within the machine keyring."). Otherwise the certificate goes to .platform, which module verification does not use.
     - The host kernel config has CONFIG_SYSTEM_TRUSTED_KEYS="" and CONFIG_SECONDARY_TRUSTED_KEYRING_SIGNED_BY_BUILTIN not set (`zgrep`, exit 0).
     - [inf] Runtime additions to .secondary_trusted_keys must be vouched for by a builtin, secondary or machine key (system_keyring.c lines 87-103, 206-218). The builtin key is a per-build ephemeral key, so a self-signed DKMS key cannot get in.
     - Conclusion [inf]: on this host, E is structurally unavoidable while Secure Boot is off and the stock Arch kernel runs. `mokutil --import /var/lib/dkms/mok.pub` alone would change nothing.
   - **KT4 is contradicted by the capture.** The question assumes the modules have "owning packages". The capture shows `pacman -Qo` exit 1, "No package owns", for all four modules (capture.txt:60-61, 79-80, 98-99, 117-118).
     - The provenance chain from DKMS to nvidia-open-dkms is not in the frozen capture. Only `pacman -Q` versions are there (capture.txt:121-125).
     - Read-only evidence I gathered: `pacman -Ql nvidia-open-dkms | grep dkms.conf` gives "/usr/src/nvidia-615.78.08/dkms.conf" (exit 0), and `stat /var/lib/dkms/nvidia/615.78.08/7.2.11-arch1-1` gives mtime 2026-10-20 09:17:22 -0300 (exit 0).
     - The letters come from `mod->taints`, which `add_taint_module` sets together with the global bit (main.c lines 194-198). The file is read-only (main.c line 1083, `__ATTR(taint, 0444, show_taint, NULL)`).
   - **KT5 is contradicted on two of its three assumed routes.**
     - Module unload: tainted-kernels.rst lines 12-13 say "Note the kernel will remain tainted even after you undo what caused the taint (i.e. unload a proprietary kernel module)".
     - Sysctl write: kernel/panic.c lines 124-129 say "Poor man's atomic or." and then call `add_taint` for each written bit, so a write can only add bits. kernel/panic.c line 103 also requires CAP_SYS_ADMIN for any write.
     - `rg 'clear_bit|tainted_mask =|tainted_mask &='` over v7.2 kernel/panic.c finds only the static initialiser at lines 59-60. Reboot is the only reset [inf: only panic.c searched, not the whole tree].
     - New narrowing: unloading leaves a further trace. main.c lines 871-873 store the unloaded module's name and taint letters in `last_unloaded_module`, and main.c lines 3972-3975 print "[last unloaded: …]" in oops module lists. The host has CONFIG_MODULE_UNLOAD_TAINT_TRACKING=y (`zgrep`, exit 0), which also lists unloaded tainted modules (`print_unloaded_tainted_modules`, main.c line 3972).
   - **KT6 is narrowed.** https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/Documentation/admin-guide/reporting-issues.rst?h=v7.2 lines 545-547 read "Your system uses a software that installs its own kernel modules, for example Nvidia's proprietary graphics driver or VirtualBox." Lines 547-548 continue "(even if they are Open Source)". The prescribed action at lines 550-553 is "temporarily uninstall such software including any modules they might have installed. Afterwards reboot." The `foo.blacklist=1` route at lines 561-562 is given for the staging-module case only.
6. [obs] A capture probe that must not be misread: capture.txt:131-132 tries `/proc/sys/kernel/panic_on_taint` and gets "No such file or directory". In v7.2, `panic_on_taint` is a boot parameter only (kernel/panic.c line 1274, `early_param("panic_on_taint", panic_on_taint_setup)`), not a sysctl. A missing file says nothing. The real answer is the empty cmdline grep at capture.txt:127-128 (exit 1, not set). No draft row misuses this, but the entry .md must not either.
