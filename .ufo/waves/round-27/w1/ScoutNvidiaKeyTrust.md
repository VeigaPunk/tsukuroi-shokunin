Verdict: holds — the KT3 and KT4 host facts are captured read-only: Secure Boot is disabled, the DKMS signing certificate is enrolled in no firmware database, no MOK list and no kernel keyring, so the correctly signed NVIDIA modules still fail kernel signature verification and set the unsigned-module taint bit next to the out-of-tree bit; all four loaded modules show the per-module letters "OE" and no package owns the module files.

1. [obs] Secure Boot is disabled. `mokutil` is not installed on this host: `/fast/scratch/hyaku/tsuku27/ScoutNvidiaKeyTrust/01-mokutil-sb-state.txt` holds "error: command not found: mokutil" with exit 127, and the `--list-enrolled` pipeline in `02-mokutil-list-enrolled-grep.txt` is empty because the binary is absent (its exit 0 is grep's or head's, not mokutil's). The answer was therefore taken from the same efivarfs source mokutil reads: `13-efivars-values.txt` shows SecureBoot attributes 6 and data byte 0, and SetupMode attributes 6 and data byte 0. The kernel agrees: `24-journal-kernel-taint-lines.txt:1` reads "Oct 22 04:55:41 plazir27 kernel: Secure boot disabled". Lockdown is "none": `12-lockdown.txt` reads "[none] integrity confidentiality". [inf] SetupMode 0 means platform keys are enrolled, so the firmware is capable of Secure Boot but it is switched off, not in setup mode.

2. [obs] There is no MOK database in this boot. The efivarfs listing in `14-efivars-secure-vars.txt` contains PK, KEK, db, dbx and their defaults but no MokList, MokListRT or MokListX variable; the sudo listing in `08-efivars-list.txt` shows SecureBoot, SecureBootSetup and SetupMode but no MokList-family variable either. [inf] No shim-style MOK enrollment can be in effect, and `mokutil --import` would have no MokManager consumer on this boot path.

3. [obs] The firmware signature database does not contain the DKMS certificate. Parsing the db efivar (`60-db-efivar.bin`) yields six X.509 entries, listed in `62-db-cert-subjects.txt`: Microsoft Windows Production PCA 2011, Microsoft UEFI CA 2011, Microsoft UEFI CA 2023, Windows UEFI CA 2023, Microsoft Option ROM UEFI CA 2023, and "CN=MSI SHIP DB" issued by "CN=MSI SHIP KEK". This matches the six keys in the kernel .platform keyring (`07-sudo-proc-keys.txt`, keyring .platform: 6). No entry is the DKMS certificate.

4. [obs] The DKMS key material exists but its certificate is self-signed and private to this machine. `04-var-lib-dkms-ls.txt` and `43-mok-file-modes.txt` show /var/lib/dkms/mok.key mode 0600 root (never read; only stat was done) and /var/lib/dkms/mok.pub mode 0644. `27-mok-pub-ski.txt` gives subject and issuer "CN=DKMS module signing key", serial 7BDE338E7B003E8FAE5C721E9063C5EF0FC88321, validity 2026-10-11 to 2126-09-17, Subject Key Identifier 14:4A:EE:CB:97:3B:01:97:9D:4D:2E:13:D1:F7:D6:72:0C:94:15:FF, and `17-mok-pub-fingerprint.txt` gives SHA-256 fingerprint CC:9A:60:7C:C7:CF:7A:D7:F2:C4:83:DE:15:8A:91:3A:8B:FD:90:01:32:55:48:A6:A1:F4:60:2A:FF:00:7F:10. [inf] Expiry is not the reason verification fails; the certificate is valid for another century.

5. [obs] All four loaded modules carry a signature made with that certificate. `09-modinfo-fields-nvidia.txt` records signer "DKMS module signing key", sig_key 7B:DE:33:8E:7B:00:3E:8F:AE:5C:72:1E:90:63:C5:EF:0F:C8:83:21 and sig_hashalgo sha512; `19-modinfo-license-signers.txt` shows the same signer for nvidia_drm and nvidia_uvm and the same sig_key for nvidia_drm; the frozen capture shows signer "DKMS module signing key" for all four (capture.txt:55,74,93,112). That sig_key is the certificate serial, not its Subject Key Identifier (`20-pubkey-hash-compare.txt` shows the SPKI hashes differ; `27-mok-pub-ski.txt` shows the serial matches). The trailer of the decompressed nvidia-drm.ko.zst is a detached PKCS#7 SignedData with SHA-512, RSA, issuerAndSerialNumber "CN=DKMS module signing key" serial 0x7BDE338E7B003E8FAE5C721E9063C5EF0FC88321, and certificates ABSENT (`64-module-signature-trailer.txt`, `65-cms-print.txt`); `openssl cms -verify -inform DER -in drm-signature.p7 -content drm-content.bin -binary -certfile /var/lib/dkms/mok.pub -nointern -noverify` exits 0 and prints "CMS Verification successful" (`66-cms-verify-mokpub.txt`). [inf] The signature is cryptographically valid over the module bytes; the signer string is metadata and is not a trust anchor.

6. [obs] The DKMS certificate is present in no kernel keyring. As root, `07-sudo-proc-keys.txt` shows .builtin_trusted_keys: 1, .secondary_trusted_keys: 1, .platform: 6, .machine: empty, and .blacklist: 445; the only kernel-generated asymmetric key listed is "Build time autogenerated kernel key" and no entry names the DKMS key or its serial (`16-proc-keys-grep.txt`). [inf] The single key in .secondary_trusted_keys is that build-time autogenerated kernel key, the same key CONFIG_MODULE_SIG_KEY="certs/signing_key.pem" names; neither the 20-byte serial nor the DKMS subject appears anywhere in the listing.

7. [obs] The kernel's verification path and the observed policy explain why E is set on a signed module. The fetched v7.2 source (https://raw.githubusercontent.com/torvalds/linux/v7.2/kernel/module/signing.c, HTTP 200, local copy `/fast/scratch/hyaku/tsuku27/ScoutNvidiaKeyTrust/src/kernel_module_signing.c`) calls verify_pkcs7_signature with VERIFY_USE_SECONDARY_KEYRING at lines 64-67, labels -ENOKEY "module with unavailable key" at lines 106-108, and only rejects the load when sig_enforce is true at lines 119-124. On this host sig_enforce reads "N" (`21-sig-enforce-sysfs.txt`) and lockdown is none (`12-lockdown.txt`), so -ENOKEY is non-fatal: the module loads, sig_ok stays false, and the v7.2 kernel/module/main.c lines 2605-2612 print "module verification failed: signature and/or required key missing - tainting kernel" and set TAINT_UNSIGNED_MODULE. The boot log has exactly that line, preceded by "nvidia: loading out-of-tree module taints kernel." (`24-journal-kernel-taint-lines.txt:2-3`). [inf] The log does not print the errno; -ENOKEY is inferred from the absent certificate plus the non-fatal branch, and [inf] if sig_enforce were Y the same module would be rejected with "Loading of module with unavailable key is rejected" (signing.c:119-121).

8. [obs] The kernel-wide taint integer is 12288, which is 0x3000, bits 12 and 13. `10-proc-sys-kernel-tainted.txt` reads 12288. The v7.2 documentation (https://raw.githubusercontent.com/torvalds/linux/v7.2/Documentation/admin-guide/tainted-kernels.rst, HTTP 200, local copy `src/Documentation_admin-guide_tainted-kernels.rst`) gives at lines 97-98 "12  _/O    4096  externally-built ("out-of-tree") module was loaded" and "13  _/E    8192  unsigned module was loaded". The per-bit letters are fixed in v7.2 kernel/panic.c lines 821-822 (source copy `src/kernel_panic.c`): TAINT_FLAG(OOT_MODULE, 'O', ' ') and TAINT_FLAG(UNSIGNED_MODULE, 'E', ' '). The O bit is applied because the module has no "intree" modinfo tag (main.c:2576-2579; `modinfo -F intree nvidia` is empty in `67-modinfo-intree-license.txt`).
