Verdict: partly holds. The host facts behind MP4 hold, but its statement that systemd-oomd monitors only kill-set cgroups is false at v262, its action premise omits a world-writable reporting socket, and the counting tool passes MP4 with a fabricated quote and a false statement.

## Findings (severity order)

**1. [obs] Defect, medium. "Only kill" is false at v262, because OOMRules= is a second monitoring channel.**
- Claim under attack: `/home/vgpnk/Projects/shokunin/tsukuroi-shokunin/corpus/knowledge/memory-pressure-r25.json:281` and `/home/vgpnk/Projects/shokunin/tsukuroi-shokunin/corpus/knowledge/memory-pressure-r25.md:203` both say "systemd-oomd monitors only cgroups whose units carry kill". The S122 row at `/home/vgpnk/Projects/shokunin/tsukuroi-shokunin/corpus/SOURCES.md:128` says "monitors only cgroups of units set to kill".
- v262 `man/systemd.resource-control.xml` lines 1633-1644 document `OOMRules=` (version tag v261 at line 1658). Lines 1642-1644 read: "will monitor this unit's cgroup and evaluate the specified rulesets against it."
- v262 `src/oom/oomd-manager.c` lines 113-118 route `OOMRules` to its own monitored map, separate from the swap and memory-pressure maps.
- The `auto` sentence overreaches in the same way. The manual says an `auto` unit "can still be a candidate" under a `kill` ancestor (`resource-control.xml` lines 1545-1548), and it never says "only". The code also builds rule-action candidates from rules-monitored cgroups (`oomd-manager.c` lines 1020-1022, 723 and 756), so an `auto` descendant of an `OOMRules=` unit is also eligible. [inf]
- Host effect now: none measured. The live sweep in finding 7 found no non-empty `OOMRules=` on any of the 987 units; the property is absent on device, target, timer, path and automount units.

**2. [obs] Defect, medium. The action premise leaves out the ManagedOOM reporting socket.**
- Claim under attack: `memory-pressure-r25.md` lines 214-215 say "Enabling the unit would still monitor nothing while every unit stays `auto`."
- The premise holds only when no reports arrive. With no reports, the memory-pressure handler returns when its map is empty (`oomd-manager.c` lines 561-563), the swap timer stays off unless its map is non-empty (lines 222-224), and the rules handler returns when its map is empty (lines 990-992).
- The daemon does accept reports from clients. It binds the method `io.systemd.oom.ReportManagedOOMCGroups` (lines 1277-1282). When it is not socket-activated, it listens on `VARLINK_PATH_MANAGED_OOM_USER` with mode `0666` (line 1288). With socket activation, the mode comes from the socket unit. The caller's uid comes from the peer (lines 237-251 and 1266). A non-root caller is accepted only for a cgroup whose owner uid equals its own uid (lines 96-111).
- Host: `systemctl show -p SocketMode -p Listen -p ActiveState -p UnitFileState -- systemd-oomd.socket` (about 11:52Z) returned `SocketMode=0666`, `Listen=/run/systemd/oom/io.systemd.ManagedOOM (Stream)`, `ActiveState=inactive` and `UnitFileState=disabled`.
- [inf] If systemd-oomd is enabled with this socket, any local account could ask it to monitor kill or rules for cgroups that account owns. No unit property would change. The monitoring would then act on those cgroups' descendants. Unit configuration therefore does not control the premise alone, and the operator needs this before enabling the unit.
- [unk] I did not start the service, so this comes from code only. I did not check the permissions of `/run/systemd/oom` because the socket is inactive. `VARLINK_PATH_MANAGED_OOM_USER` has no definition in the fetched `oomd-manager.h`, and `src/shared/varlink-util.h` returns 404 at v262.
