# Wave 2 seat RevMP6 — attack on C2 row MP6 (kernel OOM counters separate from PSI; userspace killers move neither counter)

Verdict: the row holds. The two quotes are byte-exact against the bytes the entry declares, both counted capture pointers satisfy the fixed pointer rule, and a full feeder census of Linux v7.2 shows no path by which a userspace SIGKILL moves any of the kernel OOM counters or the PSI stall totals. Two minor wording defects are recorded (finding 4 and finding 5); neither falsifies the statement, the verdict, the action, or the counted evidence, and neither changes the C2 count.

4. [obs, defect, minor] The annotation cell for pointer line 50 misattributes the oom counter to the kill path. The pointer table in corpus/knowledge/memory-pressure-r25.md (MP6, counted capture pointers) describes line 50 as "the cgroup memory.events OOM counter, the class the kernel kill path feeds". In v7.2 the kill path feeds only oom_kill and oom_group_kill: mm/oom_kill.c line 936 (MEMCG_OOM_KILL) and line 1048 (memcg_memory_event(oom_group, MEMCG_OOM_GROUP_KILL)) plus the vmstat OOM_KILL at line 935. The plain oom field has two feeders and both are OOM-declaration sites, not kill sites: mm/memcontrol.c line 1925 inside mem_cgroup_oom (the charge path), and mm/memcontrol.c line 4861 inside memory_max_write (the memory.max write retry loop). The sibling documentation agrees that oom is a declaration event: cgroup-v2.rst lines 1499 to 1504 say the cgroup's memory usage "was reached the limit and allocation was about to fail" and that the event "is not raised if the OOM killer is not considered as an option". So oom can move without any kill (for example when oom killing is disabled for the cgroup), and calling it kill-path-fed is wrong as read literally. The MP6 statement itself is not affected, because it says the kernel raises its OOM-kill counters in the kill path, which is true of oom_kill and oom_group_kill; the counted pointer line and token are also correct. Recommended fix is one word in the table cell, for example "the counter class the kernel OOM paths feed", in the entry and the JSON if the L1 amends; this is a text edit and touches no fact the checker counts.

5. [obs, defect, minor] The doc sentence the row quotes under-describes the oom_kill field, and the row's own paraphrase inherits it. cgroup-v2.rst says oom_kill counts "processes belonging to this cgroup", but in v7.2 __memcg_memory_event (mm/memcontrol.c lines 1854 to 1883) increments memory_events[] on the memcg and then on every ancestor, exiting the loop before the root memcg: "} while ((memcg = parent_mem_cgroup(memcg)) && !mem_cgroup_is_root(memcg));". That is exactly why memory.events.local exists and is documented as "not hierarchical" (cgroup-v2.rst, the memory.events.local paragraph). Concretely, a kernel OOM kill under user@1000.service would also increment oom_kill on user-1000.slice and user.slice, whose processes do not belong to those cgroups. The direction of the error is safe for the row: it makes the capture's zero at user-1000.slice slightly stronger evidence, because a zero at an ancestor also rules out kills anywhere beneath it, and the row's action paragraph already warns that a zero is one counter in one scope. No overclaim; recorded so the recheck procedure in the entry knows the field is hierarchical when reading parents against children.

6. [obs] The inference "a userspace killer's SIGKILL moves neither counter" is verified against the kernel source, not just asserted. Feeder census of Linux v7.2, all fetched from the tagged sources: MEMCG_OOM_KILL has exactly one feeder (oom_kill.c:936, kill path); MEMCG_OOM_GROUP_KILL exactly one (oom_kill.c:1048, kernel group-OOM path); vmstat OOM_KILL exactly one (oom_kill.c:935, same kill path); MEMCG_OOM two (memcontrol.c:1925 and 4861, both kernel memcg-OOM declaration sites); none of the five is reachable from signal delivery. The two userspace kill vectors are also clean: kernel/cgroup/cgroup.c (the cgroup.kill interface systemd-oomd's unit kill lands on) contains zero matches for MEMCG, and kernel/signal.c (the delivery path of any kill(2), including earlyoom's) contains zero matches for psi or memcg event calls. PSI memory stall totals are written only through psi_memstall_enter and psi_memstall_leave (kernel/sched/psi.c lines 1056 onward), called from allocation paths in mm/page_alloc.c, never from signal delivery. Therefore the kernel counters read zero unless a kernel OOM kill happened, and the signal itself adds no stall time, so the "moves neither counter" sentence is true as written.

7. [inf] No overclaim remains on the PSI half once the sentence is read as binding the kill event. A readers could misread "a userspace killer's SIGKILL moves neither counter" as "nothing moves PSI around a userspace kill"; in reality the pressure that motivated the kill moves PSI on its own, and for systemd-oomd the pressure reading is the kill's trigger by construction. The row does not say otherwise: its verdict is scoped, its action says never to read one counter as the other, and on this host the running userspace killer is earlyoom, which kills on MemAvailable thresholds rather than PSI, so its kills are not even PSI-threshold events (capture-earlyoom.txt lines 5 to 9 show the unit active and enabled; the row correctly does not claim what earlyoom reads). I judge the wording sound for a scoped verdict and would not tighten it further.

8. [obs] The version tier is exact for this host, not just for the tag. The entry cites tag v7.2 while the host runs 7.2.11-arch1-1 (capture line 6). I fetched both mm/oom_kill.c and Documentation/admin-guide/cgroup-v2.rst at stable v7.2.11 from https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git and diffed against the v7.2 bytes: oom_kill.c is byte-identical (same sha256 452f1348e79c252ee89215d55fb104591412bbcea4a3ee965e873a401f756b4e) and cgroup-v2.rst diffs to no output. Every finding above therefore holds for the running kernel's own bytes.
