# C2 MP4 cross-check — is a ManagedOOM auto cgroup ever acted on by systemd-oomd, and what would enabling it change?

Verdict: a cgroup with ManagedOOMMemoryPressure=auto and ManagedOOMSwap=auto is never monitored and never killed by systemd-oomd when no ancestor sets kill, and enabling systemd-oomd on this host as captured would produce no systemd-oomd kills because no unit on this host enables kill or sets OOMRules; the separate userspace guard earlyoom is however active and enabled on this host, so nothing in this report may be read as nothing acting before the kernel. Findings below are independent of the drafted MP4 row and come from systemd v262 primary sources plus the frozen capture; every semantic quote is taken from the upstream v262 raw files, not from the Arch rendering.

## Findings

1. [obs] systemd-oomd monitors only cgroups reported with kill. systemd-oomd.service(8), section Description: "Cgroups of units with ManagedOOMSwap= or ManagedOOMMemoryPressure= set to kill will be monitored." (13 words; quoted from https://raw.githubusercontent.com/systemd/systemd/v262/man/systemd-oomd.service.xml lines 43-44. The host package is systemd 262-1 and capture.txt:9 reads systemd 262 (262-1-arch); the Arch page https://man.archlinux.org/man/systemd-oomd.service.8.en states page version 262.1 in its footer and corroborates with identical wording, but the upstream tag is the quote authority.)

2. [obs] PID 1 filters auto-mode units out of its initial report to oomd. https://raw.githubusercontent.com/systemd/systemd/v262/src/core/varlink.c lines 123-131: the comment reads "For the initial varlink call we only care about units that enabled (i.e. mode is not set to "auto") oomd properties." (20 words) and the code at lines 128-130 skips every unit unless ManagedOOMSwap or ManagedOOMMemoryPressure equals kill or OOMRules is non-empty. With nothing matching, the initial push is not sent at all (lines 171-173, allow_empty=false).

3. [obs] Even if an auto-mode message reached oomd, oomd discards it. https://raw.githubusercontent.com/systemd/systemd/v262/src/oom/oomd-manager.c lines 124-131: when message.mode equals MANAGED_OOM_AUTO, the cgroup path is removed from the monitored hashmap and the loop continues; only non-auto messages reach the monitored-set insert at lines 206-210.

4. [obs] Kill candidates are descendants of monitored cgroups only. oomd-manager.c lines 371-384 build the candidate set solely by walking monitored cgroup paths (get_monitored_cgroup_contexts_candidates, recursively_get_cgroup_context). systemd-oomd.service(8), section Description: "only descendant cgroups are eligible candidates for killing; the unit with its property set to kill is not a candidate" (21 words; v262 man/systemd-oomd.service.xml lines 47-50), and only leaf cgroups or cgroups with memory.oom.group=1 qualify (lines 50-52). systemd.resource-control(5), section ManagedOOMSwap=auto|kill / ManagedOOMMemoryPressure=auto|kill states the one exception: "if an ancestor cgroup has one of these properties set to kill, a unit with auto can still be a candidate" (20 words; v262 man/systemd.resource-control.xml lines 1545-1548; https://man.archlinux.org/man/systemd.resource-control.5.en). With the premise "no ancestor sets kill" that path is closed, so an auto cgroup is never acted on. The same section also says: "When set to auto, systemd-oomd will not actively use this cgroup's data for monitoring and detection." (17 words, lines 1545-1546.)

5. [obs] Empty monitored sets make every detection path inert, not merely unlikely. The memory-pressure timer returns before reading anything: "Return early if nothing is requesting memory pressure monitoring" (9 words; oomd-manager.c lines 561-562). The swap event source is switched off when the swap monitored set is empty (lines 222-224). The v262 OOMRules path is gated the same way (lines 990 and 1018-1022). So with auto everywhere and no rulesets, an enabled systemd-oomd performs no swap action, no pressure action and no rules action.

6. [obs] Host state per the frozen capture, respecting the declaration's uniqueness rule: the only unique non-header line in the oomd blocks is capture.txt:73, the literal line `inactive` (exit 3). Every other value used here is non-unique and is cited by line number only, never as a uniqueness-bearing pointer: the service is disabled at capture.txt:76 and the socket disabled at capture.txt:79 (the text `disabled` occurs twice); user@1000.service, user-1000.slice, user.slice and -.slice each show ManagedOOMSwap=auto, ManagedOOMMemoryPressure=auto, ManagedOOMMemoryPressureLimit=0, ManagedOOMMemoryPressureDurationUSec=[not set], ManagedOOMPreference=none, and each of those texts occurs 4 times, at lines 112-118, 121-127, 130-136 and 139-145 (user@1000.service at 112-113, -.slice at 139-140); MemoryPressureWatch=skip at line 117 is unique but is not oomd evidence (finding 9). The oomd.conf commented defaults at capture.txt:106-108 (SwapUsedLimit=90%, DefaultMemoryPressureLimit=60%, DefaultMemoryPressureDurationSec=30s) are unique lines. The capture sha256 re-verified as e60f1bbc1feb8f251c8b276f70342da5385d07b9ad747305e1f016e0df447136 via sha256sum.

7. [obs, live reads outside the capture] No host unit or drop-in enables kill, and none sets OOMRules either. My first scan `grep -rils "ManagedOOM.*kill" /usr/lib/systemd /etc/systemd` could not have matched an `OOMRules=` line, so I repeated the scan for the second channel: `grep -rl "OOMRules" /usr/lib/systemd /etc/systemd` likewise matched only the three compiled artifacts /usr/lib/systemd/libsystemd-core-262-1.so, /usr/lib/systemd/libsystemd-shared-262-1.so and /usr/lib/systemd/systemd-oomd. `systemctl show -p OOMRules` printed the empty value `OOMRules=` for user@1000.service, user-1000.slice, user.slice and -.slice, and stat found none of /usr/lib/systemd/oomd/rules.d, /etc/systemd/oomd/rules.d, /usr/local/lib/systemd/oomd/rules.d and /etc/systemd/oomd.conf.d. The PID 1 default for both ManagedOOM properties is auto (v262 src/core/cgroup.c lines 182-185). The capture itself never reads OOMRules, so within capture-only evidence this channel stays [unk]; these live reads close it at the level of static host configuration.

8. [inf] What enabling would change on this host: systemd-oomd would start, subscribe to PID 1 through io.systemd.ManagedOOM.SubscribeManagedOOMCGroups (oomd-manager.c lines 439-441; core varlink.c lines 321-368), and receive an empty cgroup set, because findings 2, 6 and 7 show no kill unit exists here. Both monitored sets would stay empty, so by finding 5 no action would ever fire, and the configured limits never apply: SwapUsedLimit "Defaults to 90%.", DefaultMemoryPressureLimit "Defaults to 60%." and DefaultMemoryPressureDurationSec "Defaults to 30 seconds when unset or 0." (oomd.conf(5), section [OOM] Options; https://man.archlinux.org/man/oomd.conf.5.en; v262 man/oomd.conf.xml lines 172, 190, 202) matter only for monitored cgroups, and per-unit overrides are excluded: "This property is ignored unless ManagedOOMMemoryPressure=kill" (8 words; systemd.resource-control(5), v262 man/systemd.resource-control.xml lines 1555-1564 and 1571-1583). Units with kill would also gain After= and Wants= dependencies on systemd-oomd.service (same section, lines 1541-1543); with auto everywhere and no OOMRules, no unit pulls oomd in. The swap gate also needs both fractions at once: "Sets the limit for memory and swap usage on the system before systemd-oomd will take action." (16 words; oomd.conf(5), section [OOM] Options, v262 man/oomd.conf.xml lines 166-168). The conclusion "no systemd-oomd kills, no observable behavior change beyond an idle running service" is an inference from findings 1 through 7, not a live experiment, and it says nothing about other killers on this host (finding 10).

9. [obs, gating claim inf] MemoryPressureWatch=skip on user@1000.service (capture.txt:117) does not gate oomd. oomd reads the pressure stall information directly from the cgroup filesystem: v262 src/oom/oomd-util.c lines 680-686 call read_resource_pressure on the cgroup's memory.pressure file, and lines 693-711 read memory.current, memory.min, memory.swap.current and the pgscan key of memory.stat. MemoryPressureWatch= instead "Controls memory pressure monitoring for invoked processes" (7 words; systemd.resource-control(5), section MemoryPressureWatch=, v262 man/systemd.resource-control.xml lines 1662-1691), that is, the manager's own pressure watch for a service, not oomd's polling. The code citations are observed; the sentence "does not gate oomd" rests on the two citations together.

10. [obs] earlyoom, not systemd-oomd, is the live userspace guard on this host, and the capture is blind to it. My own read-only checks: `systemctl is-active earlyoom` printed `active` (exit 0), `systemctl is-enabled earlyoom` printed `enabled` (exit 0), and `pacman -Q earlyoom` printed `earlyoom 1.9.0-1`. The critic seat TsukuroiR25.CritC2Rows additionally records ActiveEnterTimestamp Thu 2026-10-22 04:55:44 -03 on this boot and the prior record at SKILL.md:1938. The MP4 wording must therefore be scoped to systemd-oomd; "nothing acts before the kernel" would be false on this host. [inf] Like oomd, earlyoom kills by userspace signal, so such kills would not raise the kernel oom_kill counters either.

## Residual risk and verification gaps

- [unk, low] The capture sampled ManagedOOM properties on four units only and never read OOMRules; within capture-only evidence the OOMRules channel stays [unk] (finding 7). My live reads close the static-configuration gap, but a runtime-created scope that set kill or OOMRules would appear in neither check. User managers default to auto like the system manager (src/core/cgroup.c lines 182-185), so this is unlikely.
- [unk] I could not observe an enabled oomd live: starting or stopping services is forbidden on this host. The conclusion rests on v262 source, v262 man pages and the frozen capture, not on an oomctl or dry-run observation. The --dry-run option added in 262 (systemd-oomd.service(8) Options) would be the safe way to verify on a machine where starting oomd is allowed.
- [inf] The earlyoom gap and the OOMRules gap are reported to the L1 as future capture fields, never absorbed into any row: the round-25 capture records neither earlyoom state nor OOMRules, so both stay [unk] inside capture-only evidence.
- [inf] v262 adds a third monitored channel, OOMRules from .oomrule files. No such rules are shipped or configured on this host (finding 7). If rules are installed later or any unit flips a ManagedOOM property to kill, the MP4 wording "never acted on" stops holding for that cgroup; the row should stay scoped to "as of the round-25 capture".
