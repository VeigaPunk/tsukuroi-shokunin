# RevengerOomHistory — why oom-event-plane.md concluded oomd "would likely have acted before the kernel"

Verdict: the line-344 claim was written on 2026-10-14 by the lane-round-6 OOM seat as a marked inference built entirely from correct measurements plus two semantic misreadings — the factory-default property values `ManagedOOMMemoryPressure=auto`/`ManagedOOMSwap=auto` were read as pre-armed configuration ("already set", i.e. yes, `auto` was read as armed), and oomd's 90 percent `SwapUsedLimit=` trigger was read as a swap-only rule when the manual defines it as a memory-AND-swap conjunction — and the sentences that refute both readings were on locally installed man pages, one of which (`systemd.resource-control(5)`) the same file already cites by name one table row below the wrong line; three verification layers then kept the sentence alive because every one of them verified measurements, code contracts, or freshness, never the property semantics.

3. [obs] Yes — `auto` was read as armed. The cell bolds "**already set**" for the two `auto` properties and the adjacent inference cell uses them as the bridge to "oomd would likely have acted *before* the kernel". Under systemd's documented semantics the reading is inverted twice. First, `auto` is nobody's configuration: `systemd.resource-control(5)` says the pair "Defaults to `auto`" (v262 source `man/systemd.resource-control.xml:1529`), so every unit on the host reports `auto` unless an operator changed it — the capture of `user@1000.service`, `user-1000.slice`, `user.slice` and `-.slice` reading `auto` is the untouched factory state, not evidence of setup. Second, `auto` disarms rather than arms: "When set to `auto`, systemd-oomd will not actively use this cgroup's data for monitoring and detection" (`man/systemd.resource-control.xml:1545-1546`), while only "When set to `kill`, the unit becomes a candidate for monitoring" (`:1531`), and `systemd-oomd.service(8)` states "Cgroups of units with `ManagedOOMSwap=` or `ManagedOOMMemoryPressure=` set to `kill` will be monitored" (`man/systemd-oomd.service.xml:43-44`). So in the counterfactual world where oomd had been enabled, an all-`auto` host with no ancestor at `kill` (and, in 262, no `OOMRules=`) would have given oomd zero monitored cgroups from these units; `auto` units could only die as descendants of a `kill` ancestor. The round-8 deep note repeated the same armed reading and even recorded `ManagedOOMMemoryPressureLimit=0` "(=default)" as relevant, although that property "is ignored unless `ManagedOOMMemoryPressure=kill`" (`resource-control.xml:1563`, same for the duration at `:1582`) — `corpus/knowledge/kill-event-deep-r8.md:255` ("`ManagedOOMSwap=auto` **and** `ManagedOOMMemoryPressure=auto` are already set on ..."), commit `72b038d`.

4. [obs] The "90 % swap rule" is a memory-AND-swap conjunction, and its memory half was never measurable. `oomd.conf(5)` v262 defines `SwapUsedLimit=`: "If the fraction of memory used and the fraction of swap used on the system are both more than what is defined here, systemd-oomd will act on eligible descendant control groups with swap usage greater than 5% of total swap" (`man/oomd.conf.xml:166-169`, "Defaults to 90%" at `:172`). Round 6's inference compared only the swap plane (event B ≈99.9 %, event A 100 %) against the 90 percent figure and concluded "above oomd's 90 % swap rule ... oomd would likely have acted before the kernel" (`oom-event-plane.md:344`); round 8 sharpened it to "the swap rule (90 %) is below event A's measured 99.9999 % saturation, so oomd would have had a trigger" (`kill-event-deep-r8.md:255`). The system memory fraction at either kill second was never measured and, by the lane's own record, cannot be: no pre-kill capture exists ("event B's 'before' picture exists nowhere", `kill-event-deep-r8.md` row 11; erratum E4 re-dates the swap maxima as lifetime, not 13:10:59 values), and the note itself teaches that a cgroup memory peak "is not a pressure reading" (`oom-event-plane.md`, §4.4). [inf] Even with oomd enabled and a unit at `kill`, the trigger premise rests on an undatable half-condition; the counterfactual was asserted from swap alone.

5. [inf] Why the round-6 author fell into it — the mechanism visible in the artifacts. A `systemctl show -p ManagedOOM*` dump cannot distinguish an explicitly configured value from a compiled-in default, so "auto" looks like configuration ("already set") unless the property's manual text is read. The section's frame was "prevention options — how close was this host to having a guard" (`oom-event-plane.md` §7 preamble: "Nothing in this table was changed by this lane; every 'current state' cell is a measurement"), and the author had just extracted the three oomd defaults from `oomd.conf(5)` (round 8's ledger explicitly lists the read: "`/etc/systemd/oomd.conf`, `oomd.conf(5)` ..." at `kill-event-deep-r8.md:327`), which supplies exactly the number a single-variable comparison wants. The correct ManagedOOM clauses sit on a page the same file cites for a different clause one row later: row 4 attributes the `$MEMORY_PRESSURE_WATCH` export semantics "per `systemd.resource-control(5)`" (`oom-event-plane.md:347`), and the refuting entries are in that same page's "Memory Pressure Control" section, two entries above `MemoryPressureWatch=`. The author consulted the page for the pressure-watch clause and never for the ManagedOOM clauses directly above it.
