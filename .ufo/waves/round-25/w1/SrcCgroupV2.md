# SrcCgroupV2 — C2 source for MP3 and MP6 (Linux v7.2 cgroup v2 documentation)

Verdict: the single upstream page `Documentation/admin-guide/cgroup-v2.rst` at tag `v7.2` (byte-identical to the host's kernel version) carries located quotes for both rows I own: it names the per-cgroup `memory.pressure` file and its hierarchy-aggregation semantics (MP3), and it defines the `memory.events` keys `oom`, `oom_kill` and `oom_group_kill` while stating that `memory.events` exists only on non-root cgroups (MP6). The kernel-source facts seat `SrcPsiDoc` relayed for MP3 — the root cgroup mapping onto the system pressure group, and the per-cgroup stall accumulator's creation-scoped epoch — I re-opened and re-verified myself at the `v7.2` tag. One correction to the relayed framing is recorded in finding 9: the per-cgroup `total` values are **not** hierarchically nested sums, so the page's "aggregates it at each level of the hierarchy" sentence must not be read as "a parent's total contains its children's totals"; I measured this on the live host.

This is what makes the capture's per-cgroup totals (lines 34-35, 38-39, 42-43) legitimately differ from each other and from the system totals.

## 4. Finding that qualifies the page's aggregation sentence (MP3)

9. [obs] The capture's per-cgroup `total` values are **not** hierarchically nested: `user.slice` reads `total=3150158` (capture line 34), its child `user-1000.slice` reads `total=3158801` (line 38), and the grandchild `user@1000.service` reads `total=3161820` (line 42). A parent whose total were the sum of its children's would be the largest; here each descendant reads slightly larger than its parent. The same inversion holds for `full` (lines 35, 39, 43).

10. [obs] I reproduced this on the live host, read-only, twice. Over a 30-second window the `some` totals grew by 536 µs for `user.slice`, 549 µs for `user-1000.slice` and 556 µs for `user@1000.service`; over a 90-second window by 2114 µs, 2414 µs and 2400 µs respectively, while the root cgroup (the system group) grew by 513823 µs and `system.slice` by 0 µs. Cumulative `some` totals at the end of the 90-second window: root 49615923, `system.slice` 29701, `user.slice` 3546801, `user-1000.slice` 3549995, `user@1000.service` 3551468. The parent-to-child ordering is inverted in every reading, and the three user-slice values are within 0.14 % of one another.

11. [inf] The mechanism is visible in the source I re-verified. `kernel/sched/psi.c` line 1127 sets `cgroup->psi->parent = cgroup_psi(cgroup_parent(cgroup));`, and the `for_each_group` macro at lines 793-794 walks `iter = iter->parent`, so a stall in a task's default cgroup is recorded into that group's per-CPU state *and* into each ancestor group's. The ancestor therefore accumulates the same stall events, but it does not add the child's already-counted total on top: `collect_percpu_times` at lines 362-415 accumulates into each group's own `group->total` from that group's own per-CPU state buckets, and the exported value at lines 1286-1287 is `div_u64(group->total[PSI_AVGS][res * 2 + full], NSEC_PER_USEC)`. Each group's exported `total` is that group's own accumulated stall time, not a sum over its subtree. The parent and child totals are close because they see largely the same stall events; the small residual differences come from the different creation epochs and from tasks whose default cgroup differs.

12. [inf] Consequence for the MP3 wording: the page's sentence (MP3-b, lines 1077-1078) — "PSI accounts stalls for each cgroup separately and aggregates it at each level of the hierarchy" — describes the accounting being aggregated up the hierarchy, and it is accurate in that sense. It must **not** be read as "a parent's `total` includes its children's `total`", and it must not be used to argue that a parent's counter is greater than or equal to a child's. The capture's lines 34-43 are the evidence that the exported values are independent per-cgroup accumulators. [unk] Whether the page's sentence is precise enough on this point for a learner is a judgment for the L1; the honest fix inside the MP3 row is to say the per-cgroup files report each cgroup's own accumulated stall time with its own epoch, and that the root cgroup's file is the system view by kernel design.

13. [obs] What this does **not** change: the root cgroup's file is still the system view (finding 3 above), the per-cgroup epoch still differs from the system epoch, and the six per-cgroup capture lines remain unique anchors. Only the "parent contains child" reading is withdrawn.

14. [obs] A second, smaller caveat on the same point: the live 90-second reading shows `system.slice` at `total=29701` and `user.slice` at `total=3546801` — the two are not comparable either, since the numbers are per-cgroup accumulators with per-cgroup epochs, not shares of one system total.
