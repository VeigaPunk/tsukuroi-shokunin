## Finding — contradicted host-reading claim
Severity: substantive knowledge defect; blocks admission. Frozen entry lines 233-235 say: “a replace that the resume path set to suspended without taking the exclusive operation (dev-replace.c:1235-1242) shows in neither”. This is false for replace_target. The cited branch only changes replace_state to SUSPENDED and returns; it does not clear the target bit (S247 dev-replace.c:1235-1242). In the same pinned source, restoring a STARTED or SUSPENDED replace finds its target (dev-replace.c:170-174), and, when present, sets BTRFS_DEV_STATE_REPLACE_TGT (dev-replace.c:196-210). The resume path reaches the exclusive-operation attempt only after the target-present/bdev check (dev-replace.c:1218-1235). Thus the failed-exclusive-operation branch does not imply an absent/unmarked target. S243 sysfs.c:2015-2017 reports that bit as 1, independently of replace_state or exclusive_operation. The row's own setup/finish citations (dev-replace.c:309 and :970) also show that the target bit is not controlled by this suspend branch.

The sentence correctly begins by denying that these attributes expose the replace-state enum, but its following example overclaims invisibility of the replace itself: replace_target still exposes the target role. If “shows in neither” intended only the SUSPENDED enum, it must say that explicitly rather than contradict the preceding target-bit description. This is a code-path counterexample, not a live-host reproduction.

Exact replacement for the two sentences beginning “Neither file reports” through “ongoing.”:

“Neither file reports the replace-state enum itself. If the resume path cannot acquire the exclusive operation, it sets the replace state to suspended and returns without clearing the target bit (dev-replace.c:1235-1242); exclusive_operation does not identify that replace, but replace_target still reads 1 for its marked target (sysfs.c:2015). A valid suspended replace still counts as ongoing (dev-replace.c:1278-1287).”
