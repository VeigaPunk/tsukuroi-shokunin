## Finding — medium severity: suspended replace can remain visible through replace_target

The Host reading's sentence says: "a replace that the resume path set to suspended without taking the exclusive operation (dev-replace.c:1235-1242) shows in neither". Taken as the stated claim that neither attribute indicates this replace, this is contradicted by the pinned code. Failure to acquire the exclusive operation does not clear the target bit. It only sets SUSPENDED and returns (S247 dev-replace.c:1235-1242). Moreover, that branch is reached only after the target-device/bdev check at dev-replace.c:1218-1227 succeeds. On restoring a started/suspended replace, dev-replace.c:170-174 resolves the target, and dev-replace.c:196-210 sets its REPLACE_TGT bit when present. Initial target setup likewise sets that bit at dev-replace.c:309. The resume failure branch never clears it; sysfs.c:2015-2017 therefore continues to return 1 for that target. This is an indication of replace activity, although it does not distinguish STARTED from SUSPENDED. The separate exclusive_operation attribute can name the competing operation (sysfs.c:1271-1298), not this replace. The row correctly distinguishes state from partial indications earlier, but its categorical "shows in neither" discards that distinction.

Exact replacement for the two sentences beginning "Neither file reports":

"Neither file reports the replace state itself. If the resume path fails to take the exclusive operation and sets the replace to suspended (dev-replace.c:1235-1242), exclusive_operation does not identify that replace, but replace_target still reports the target bit (sysfs.c:2015); that failure branch does not clear it. Thus these files do not distinguish a suspended replace from a started one solely from the target bit."

This is a contradicted clause, hence fails rather than partly. No admission mark is written. Recommendation only; not an admission or integration decision.
