     5	# The btrfs scrub status record: who writes it, what it holds, and what its absence means (round 42)
     6	
     7	Scope: the storage-integrity frontier (`PROVINCE.md` Frontier, scrub record; `corpus/README.md` `## Frontier`).
     8	The lane already holds what scrub verifies and repairs and that `btrfs scrub status` reads a file under
     9	`/var/lib/btrfs` (`corpus/knowledge/storage-health-r26.md` SH3, SH4; S129, S139). It held no statement of the record
    10	itself: how the file is named and replaced, its line format, which process writes it and when recording is
    11	switched off, and how the status command turns per-device lines into one filesystem verdict. Those decide whether
    12	"no record" may be read as "never scrubbed". Rows SC1-SC5 state upstream behaviour of btrfs-progs v7.1 (the
    13	version this host runs) from `cmds/scrub.c` and `CHANGES`; the host readings are this machine's, unprivileged.
    14	Nothing here runs a scrub, writes `/var/lib/btrfs` or changes a scrub limit (operator actions).
    15	
    16	## SC1
    17	
    18	**Statement.** The record for one filesystem is the file `/var/lib/btrfs/scrub.status.<fsid>` (the base path plus a
    19	dot plus the filesystem UUID). Every update is written to a sibling file `scrub.status.<fsid>_tmp` and then moved
    20	over the record with `rename`, so a reader sees either the old or the new record, never a half-written one. A file
    21	the CLI creates gets mode 0600, and every open, for reading or writing, must take a non-blocking exclusive `flock`
    22	(`LOCK_EX`), so a second writer or a reader that finds the lock held fails at once instead of waiting.
    23

    39	## SC2
    40	
    41	**Statement.** The record is text. Its first line is `scrub status:1` (format prefix and version 1). Each further
    42	line belongs to one device: the filesystem UUID, a colon, the device id, then one `|key:value` pair per field, in
    43	this order — the progress counters `data_extents_scrubbed`, `tree_extents_scrubbed`, `data_bytes_scrubbed`,
    44	`tree_bytes_scrubbed`, `read_errors`, `csum_errors`, `verify_errors`, `no_csum`, `csum_discards`, `super_errors`,
    45	`malloc_errors`, `uncorrectable_errors`, `corrected_errors`, `last_physical`, then the run fields `t_start`,
    46	`t_resumed`, `duration`, `canceled`, `finished`. A record therefore carries per-device error sums and a per-device
    47	finished flag, not one filesystem verdict.
    48

    61	## SC3
    62	
    63	**Statement.** The record is written by the userspace `btrfs scrub start` process, not by the kernel: it writes an
    64	all-zero record when the scrub starts and progress records while it runs. Recording is switched off, with a
    65	warning that ends "status recording disabled", when the directory `/var/lib/btrfs` cannot be created or the first
    66	record cannot be written; the scrub itself still runs. Whether a scrub is running is asked from the kernel with the
    67	`BTRFS_IOC_SCRUB_PROGRESS` ioctl per device, independent of the file. So a missing record does not prove that no
    68	scrub ran: a scrub whose recording was disabled, or one driven by another tool through the ioctl, leaves none.
    69

    85	## SC4
    86	
    87	**Statement.** `btrfs scrub status` treats a missing record as no history (an open failure of `ENOENT` is not an
    88	error; any other open failure prints a warning). The filesystem summary folds the per-device lines together: the
    89	start time is the smallest device start (`_SCRUB_FS_STAT_ZMIN`, where an unset value is always replaced), the run
    90	counts as canceled if any device was canceled, and it counts as
    91	finished only if every device's record is finished (the flag starts at 1 and takes the minimum, `_SCRUB_FS_STAT_MIN`).
    92	The status word is `running` when the kernel reports a scrub in progress, else `aborted` when canceled, else
    93	`finished`, else `interrupted`; with no start time the summary prints `no stats available` instead. An
    94	`interrupted` status therefore means an unfinished record with nothing running now (for example a start process
    95	that ended before the scrub did), not a device error.
    96

   100

   102

   114	## SC5
   115	
   116	**Statement.** Each device has a scrub throughput limit in sysfs, `/sys/fs/btrfs/<fsid>/devinfo/<devid>/scrub_speed_max`
   117	(bytes per second; 0 means no limit). `btrfs scrub status` and `btrfs scrub start` read it and report a set limit,
   118	and `btrfs scrub limit` shows or sets it; all three arrived in btrfs-progs 6.6.3. A failed read is reported as 0,
   119	so the status command cannot tell "no limit" from "limit unreadable" (on a kernel without the file the limit
   120	silently reads as none). A scrub that looks slow should be checked against this file before the device is blamed.
   121	
   122	**Quote.** `S237` scrub.c:1215: "snprintf(path, sizeof(path), "devinfo/%llu/scrub_speed_max", devid);"
   123	
   124	**Quote.** `S237` scrub.c:1218: "limit = 0;"
   125	
   126	**Quote.** `S238` CHANGES:460: "btrfs-progs-6.6.3 (2023-12-14)"
   127	
   128	**Quote.** `S238` CHANGES:467: "* scrub status: report limit if set in sysfs/../scrub_speed_max"
   129	
   130	**Quote.** `S238` CHANGES:468: "* scrub limit: new command to show or set the per-device scrub limits"

   134	## How this changes OS triage
   135	
   136	- Read "no scrub record" as `UNRECORDED`, not `NEVER SCRUBBED` (SC3); the lane's SH4 verdict `UNVERIFIED` for stored
   137	  data stands.
   138	- A record is per device; a filesystem `finished` needs every device finished, and one canceled device makes the
   139	  whole run `aborted` (SC2, SC4).
   140	- `interrupted` is a process outcome (an unfinished record, nothing running), not a media fault; read the error
   141	  sums in the per-device lines (`btrfs scrub status -d`, raw `-R`) before calling the device (SC4).
   142	- Before reading a slow scrub as a device problem, read `scrub_speed_max` (SC5).
