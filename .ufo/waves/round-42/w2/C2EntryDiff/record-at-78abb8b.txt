     5	# The btrfs scrub status record: who writes it, what it holds, and what its absence means (round 42)
     6	
     7	Scope: the storage-integrity frontier (`PROVINCE.md` Frontier, scrub record; `corpus/README.md` `## Frontier`).
     8	The lane already holds what scrub verifies and repairs and that `btrfs scrub status` reads a file under
     9	`/var/lib/btrfs` (`corpus/knowledge/storage-health-r26.md` SH3, SH4; S129, S139), including the record's name
    10	pattern (SH4) and that a scrub run with recording disabled cannot be excluded (SH4 note). It held no statement of the
    11	record itself: how the file is replaced, its line format, which process writes it and when recording is switched off,
    12	how the status command turns per-device lines into one filesystem verdict, and the per-device throughput limit that
    13	same command reports (SC5). Those decide how far "no record" may be read as "never scrubbed". Rows SC1-SC5 state upstream behaviour of btrfs-progs v7.1 (the
    14	version this host runs) from `cmds/scrub.c` and `CHANGES`; the host readings are this machine's, unprivileged.
    15	Nothing here runs a scrub, writes `/var/lib/btrfs` or changes a scrub limit (operator actions).
    16	
    17	## SC1
    18	
    19	**Statement.** The record for one filesystem is the file `/var/lib/btrfs/scrub.status.<fsid>` (the base path plus a
    20	dot plus the filesystem UUID; the name pattern is already held, SH4). Every update is written to a sibling file `scrub.status.<fsid>_tmp` and then moved
    21	over the record with `rename`, so a reader sees either the old or the new record, never a half-written one. A record or
    22	`_tmp` file the CLI creates gets mode 0600 (the `open` mode argument, subject to the umask), and every open of either,
    23	for reading or writing, must take a non-blocking exclusive `flock` (`LOCK_EX`), so a second writer or a reader that
    24	finds the lock held fails at once instead of waiting. (The progress socket `/var/lib/btrfs/scrub.progress.<fsid>` is a
    25	different file, created by `bind`, not covered here.)

    42	## SC2
    43	
    44	**Statement.** The record is text. Its first line is `scrub status:1` (format prefix and version 1). Each further
    45	line belongs to one device: the filesystem UUID, a colon, the device id, then one `|key:value` pair per field, in
    46	this order — the progress counters `data_extents_scrubbed`, `tree_extents_scrubbed`, `data_bytes_scrubbed`,
    47	`tree_bytes_scrubbed`, `read_errors`, `csum_errors`, `verify_errors`, `no_csum`, `csum_discards`, `super_errors`,
    48	`malloc_errors`, `uncorrectable_errors`, `corrected_errors`, `last_physical`, then the run fields `t_start`,
    49	`t_resumed`, `duration`, `canceled`, `finished`. A record therefore carries per-device error sums and a per-device
    50	finished flag, not one filesystem verdict.

    64	## SC3
    65	
    66	**Statement.** The record is written by the userspace `btrfs scrub start` process, not by the kernel: it writes an
    67	all-zero record when the scrub starts (or is resumed) and progress records while it runs. Recording is switched off, with a
    68	warning that ends "status recording disabled", when the directory `/var/lib/btrfs` cannot be created or the first
    69	record cannot be written; the scrub itself still runs. Whether a scrub is running is asked from the kernel with the
    70	`BTRFS_IOC_SCRUB_PROGRESS` ioctl per device, independent of the file. A record-write failure later in the run
    71	ends the progress writes without that warning; only the final write reports a failure ("failed to record the
    72	result"). So a missing record does not prove that no scrub ran: a scrub whose recording was disabled, or one driven
    73	by another tool through the ioctl [inference from the write path], leaves none. That conclusion was already held
    74	(SH4 note); new here are the mechanism and the disable conditions.

    91	## SC4
    92	
    93	**Statement.** `btrfs scrub status` treats a missing record as no history (an open failure of `ENOENT` is not an
    94	error; any other open failure prints a warning and the command exits with an error). The filesystem summary folds the per-device lines together: the
    95	start time is the smallest device start (`_SCRUB_FS_STAT_ZMIN`, where an unset value is always replaced), the run
    96	counts as canceled if any device was canceled, and it counts as
    97	finished only if every device that has a record in the file is finished (the flag starts at 1 and takes the minimum,
    98	`_SCRUB_FS_STAT_MIN`; devices without a record are skipped).
    99	The status word is `running` when the kernel reports a scrub in progress, else `aborted` when canceled, else
   100	`finished`, else `interrupted`; with no start time the summary prints `no stats available` instead. An
   101	`interrupted` status therefore means an unfinished record with nothing running now (for example a start process
   102	that ended before the scrub did) [inference], not a device error.
   103

   122	## SC5
   123	
   124	**Statement.** Each device has a scrub throughput limit in sysfs, `/sys/fs/btrfs/<fsid>/devinfo/<devid>/scrub_speed_max`
   125	(bytes per second; 0 means no limit). `btrfs scrub status` and `btrfs scrub start` read it and report a set limit,
   126	and `btrfs scrub limit` shows or sets it; all three arrived in btrfs-progs 6.6.3. A failed read is reported as 0,
   127	so the status command cannot tell "no limit" from "limit unreadable" (on a kernel without the file the limit
   128	silently reads as none). A scrub that looks slow should be checked against this file before the device is blamed.
   129	
   130	**Quote.** `S237` scrub.c:1215: "snprintf(path, sizeof(path), "devinfo/%llu/scrub_speed_max", devid);"
   131	
   132	**Quote.** `S237` scrub.c:1218: "limit = 0;"
   133

   142	## How this changes OS triage
   143	
   144	- Read "no scrub record" as a gap in evidence (`UNVERIFIED`, SH4), not as "never scrubbed" (SC3); what SC3 adds is
   145	  the mechanism, not a new verdict.
   146	- A record is per device; a filesystem `finished` needs every device that has a record finished, and one canceled
   147	  device makes the whole run `aborted` (SC2, SC4).
   148	- `interrupted` is a process outcome (an unfinished record, nothing running), not a media fault; read the error
   149	  sums in the per-device lines (`btrfs scrub status -d`, raw `-R`) before calling the device (SC4).
   150	- Before reading a slow scrub as a device problem, read `scrub_speed_max` (SC5).
