## Findings

1. **MEDIUM — ambient global/system Git configuration can execute in fixture selftests before C1.** [obs] The target wrappers at `check-boot-chain.py:802-807`, `check-recheck-commands.py:799-805`, `check-section-citations.py:568-575`, `check-seat-scope.py:174-179`, and `check-source-scope-correction.py:355-359` inherit non-`GIT_*` environment including HOME and do not set `GIT_CONFIG_NOSYSTEM`/`GIT_CONFIG_GLOBAL`. [obs] Their selftests run mutating Git commands in fresh repositories: boot-chain `:1338-1382`; recheck `:1081-1093,1132-1137`; section citations `:595-611`; seat scope `:291-316`; source scope `:445-455`. [inf] If the invoking user's system/global config supplies a `core.hooksPath` with an executable hook, a target selftest can run it on commit/checkout (and section-citations can run a pre-push hook on its local push); applicable filters may also run on `git add`. Impact is code execution as the gate user. The allow-list's NOSYSTEM/GLOBAL settings close this ambient-config path; they do not make repository-local config inert. Smallest remediation: apply the exact allow-list to every Git-spawning helper, including the distinct helpers at `check-locator-clarification.py:583-585`, `check-section-citations.py:567-575`, and `measure-update-recheck.py:484-490` (the latter two already have some config suppression).

2. **LOW — repository-local include reads survive the allow-list.** [obs] The probe's two revision-mode lane readers run Git against the supplied clone (`check-btrfs-repair-r31.py:117,121,178,192-193`; `check-btrfs-space-r30.py:101,105,378-379`). Git still parses repository-local config and follows `include.path`/`includeIf`; global/system suppression and removal of HOME do not suppress local includes. [inf] A hostile local include can make Git open a chosen config file, but the commands observed here are object/plumbing reads and do not expose evidence of executing `core.fsmonitor`, `core.hooksPath`, `core.sshCommand`, filters/`diff.external`, or `credential.helper`. No output evidence shows included file contents being disclosed. Smallest remediation if local config is in the threat model: read from a config-isolated scratch repository/object copy; the proposed environment alone cannot disable local config. Otherwise retain the read-only command set and document this residual.

3. **LOW — fixture-local settings are not intrinsically sandboxed.** [obs] Seven probe targets create fresh temporary repositories; the code does not import the lane repository's `.git/config`. [inf] If a same-user actor could plant local config into one of those temp repositories before later Git commands, hooks/filters may run where the test issues add/commit/checkout/push. This is not an input path from the lane clone in the frozen probe. The allow-list does not change this local-config behavior; the smallest practical mitigation is to keep these directories private and fresh and not reuse caller-supplied repository paths.

[obs] Config-key summary: `include.path`/`includeIf` is the persistent local read path; `core.fsmonitor` is not queried by the lane object/plumbing commands; `core.hooksPath` and applicable clean filters can matter only for mutating fixture commands; no lane command invokes SSH transport, external diff/textconv, or credential transport. The citations selftest pushes only to a local bare repository (`check-section-citations.py:601-605`).

[inf] Operability: `PATH=/usr/bin:/bin` includes `/usr/bin/git` (the repair target itself uses that absolute binary at `check-btrfs-repair-r31.py:117`). Fixture identity is configured locally or explicitly in the selftests; no dependency on HOME for Git identity was found. No operability blocker is evident from the requested allow-list. [unk] No target was executed and no actual lane-local `.git/config` or included file was inspected; this is a source-only assessment, not a claim about live configuration.
