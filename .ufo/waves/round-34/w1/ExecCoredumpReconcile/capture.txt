Equality checks:
- census coredump= EQUALS the sum of all first-MESSAGE-line kinds at both captures
  (1621 = 183+1365+69+4; 1635 = 183+1379+69+4). The awk counts every systemd-coredump entry.
- census coredump= does NOT equal 'dumped core' only (183 at 08:44Z, 183 at 08:49Z).
- census coredump= is 4 more than coredumpctl's boot-window length in both captures
  (1621-1617, 1635-1631): the 4 extra are `coredump_receive` handler errors with no
  MESSAGE_ID (CODE_FUNC=coredump_receive, CODE_LINE=100, PRIORITY=3, ERRNO present, 44-char
  MESSAGE, i.e. the `log_error_errno` at v262 src/coredump/coredump-receive.c:100).
- A2 also shows `coredumpctl list --since '2026-10-22 07:55:41'` returning 1616: systemd
  parses that wall-clock string in the local zone (-03), i.e. 10:55:41Z, one record after the
  true boot start; the @epoch window (1617) is the boot-0 figure used above.
- coredumpctl's length is not a core-file count either: every record in the boot window has
  `"corefile":"none"` and size null (Storage=none, section D); 0 of those 1617/1631 values
  names an existing file, and /var/lib/systemd/coredump holds only 2 stale files dated
  2026-10-20 (names not printed), i.e. from before that boot.

Why the JSON-null class exists (measured, same capture bytes):
- Default `journalctl -o json` omits long fields: v262 src/shared/logs-show.c:43 defines
  JSON_THRESHOLD 4096U and :1124 emits JSON null when
  `!(flags & OUTPUT_SHOW_ALL) && strlen(name) + 1 + size >= JSON_THRESHOLD`; :1219 also sets
  the journal data threshold to 4096 unless OUTPUT_SHOW_ALL (`-a`) is given.
- With `-a` on the same boot and minute (08:50:22Z): 1635 systemd-coredump entries become
  252 'dumped core' + 1379 'terminated abnormally...' + 4 other, 0 JSON null.
- Exactly 69 of the 252 'dumped core' messages are >= 4089 chars (4089 + len("MESSAGE") + 1
  = 4096), which is exactly the 69 default-view nulls; the longest default-view 'dumped core'
  MESSAGE is 3692 chars. So the null class is a journalctl display default, not a crash class.
- COREDUMP_PROC_MAPS is null for 1620 of 1635 default-view entries and for 4 with -a.

What one counted entry is: one crash-report journal record written by
`coredump_submit` (CODE_FILE ../systemd/src/coredump/coredump-submit.c, CODE_LINE 793, the
`sd_journal_sendv` at v262 coredump-submit.c:793), one per crash (1617 records had 1617
distinct COREDUMP_PID@COREDUMP_TIMESTAMP keys), whose MESSAGE is either
"Process <pid> (<comm>) of user <uid> dumped core." or the same sentence ending
"terminated abnormally without generating a coredump." (source: v262 coredump-submit.c:711).
The two variants are a per-record branch on whether systemd-coredump processed a core, so
the class mixes both and the number is not a coredump count.

## E. Plain answer

At both capture times the census's `coredump=` (and therefore the ADJ-04
`class=coredumps value=`, which is the same variable) equals the sum of all first-MESSAGE-line
kinds: every journal entry whose SYSLOG_IDENTIFIER is systemd-coredump, without regard to
whether a core was produced. It is not the 'dumped core' count: 183 of 1621 at 08:44Z and
183 of 1635 at 08:49Z in the default JSON view (252 of 1635 with `-a`, because 69 long
messages are nulled by journalctl's 4096-byte JSON threshold). Four entries are not crash
records at all but `coredump_receive` errors. The figures drift with every non-core crash
report: +14 in five minutes, all in the 'terminated abnormally without generating a
coredump' class, while 'dumped core' stayed 183. `coredumpctl list` in systemd 262 has no
`-b` option (argv error, exit 1); its boot-0 window length equals the crash-record count
(1617/1631) and every record shows `"corefile":"none"` under Storage=none, so it is not a
core-file count either.
