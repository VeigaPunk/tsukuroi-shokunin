## Findings

1. [obs] Every builder is a deny-list of the `GIT_`/`LD_`/`PYTHON` prefixes followed by an update (the "Builder" column above). I found no other `subprocess`, `os.system`, `exec*` or `Popen` site in the 12 files. I listed every spawn site by grepping each file for `subprocess.run|Popen|call|check_output|os.system|exec|spawn|env=|sys.executable`; the full output is in this session's command log, and the rows above are its result.
2. [obs] Strace of each target under a probe-style control environment confirms the leak and the program set. Every child received 259 of the 261 ambient names unchanged. The builders override only HOME and XDG_CONFIG_HOME; PATH and LC_ALL were already `/usr/bin:/bin` and `C` in the ambient environment. Programs started:
   - git (/usr/bin/git and /usr/lib/git-core/git) by all 11 targets;
   - `python3` by targets 2, 7, 8, 10 and 11;
   - `/usr/bin/bash` by target 9 only (17 times);
   - `/bin/sh` and git-upload-pack by targets 10 and 11, started by `git clone`.
   Evidence: `.ufo/waves/round-32/w1/ScoutSpawnSitesR32/trace_summary.txt`, produced by `timeout 300 python3 trace_summary.py`, exit 0. Example line: `/usr/bin/bash x17 | ambient passed unchanged: 259 of 261 | overridden: HOME,XDG_CONFIG_HOME`.
3. [obs] The only names git adds for its own children are GIT_* names: GIT_AUTHOR_*, GIT_CONFIG_PARAMETERS, GIT_EXEC_PATH, GIT_PREFIX, GIT_PROTOCOL, GIT_DIR and GIT_NO_LAZY_FETCH (trace_summary.txt, "added" column). An allow-list at the tool's builder therefore also closes git's grandchildren [inf].
4. [obs] Children need no ambient name to keep output identical. Each of the 11 targets ran once under the control environment (mode A) and once under `env -i PATH=/usr/bin:/bin` (mode B), with the probe's argv, in fresh copies of `git archive fe1ae02`:
   - All 11 had rc=0 in both modes, with equal normalised stdout digests.
   - 9 of 11 were byte-identical (`cmp`).
   - The two owed-statement batteries differ only in commit SHAs. Their fixture commits get fresh timestamps on every run, so this happens between any two runs, and the probe's 40/64-hex normalisation removes it.
   - No stdout from any target contained a `/tmp`, `/fast/scratch` or `/home/` path.
   Evidence: `.ufo/waves/round-32/w1/ScoutSpawnSitesR32/envi-runs.txt`, produced by `timeout 2400 xargs -P4 -L1 ./run_one.sh < jobs.txt` and `jobs2.txt`, both exit 0. Example lines: `check-self-assessment-B rc=0 secs=1 stdout_lines=260 norm=35e28764be9bc6b1` (equal to A); `mutants-kernel-taint-B rc=0 ... norm=a70ddc3b5f683870` (equal to A).
5. [inf] What each builder must keep is therefore exactly the names it already writes (the "Names the builder sets itself" column). The executors can start each builder from `{}` instead of `os.environ`. There are two optional additions:
   - **TMPDIR**: it only moves where the python children's temporary files go, and no stdout path depends on it (finding 4). The probe never injects TMPDIR (docstring lines 24-29), so passing it through cannot be counted as a leak.
   - **HOME in row 12**: `check-owed-statements-r29.py` takes HOME and XDG_CONFIG_HOME from the ambient environment. In the targets that HOME is already the parent mutant's private HOME, and under `env -i` (no HOME at all) the output did not change. Keeping HOME as "copy if set" or making it private both keep parity [inf].
6. [inf] Rows 7, 8, 10 and 11 start the counter from `--counter-rev` = `{rev}` as a python child, and the counter's own git children (grandchildren of the target) come from the counter's builder. Two consequences:
   - Fixing only the mutant is enough to make these four targets non-leaking. The probe counts injected names in every traced execve after the first, so the python counter must receive a clean environment. A counter that still copies `os.environ` then only passes on that already-clean environment, so its git children get no injected name.
   - The counter builders (rows 1, 3 and 12) still need the allow-list for their own direct runs. Row 1 and row 3 are probe targets in their own right (their `--selftest` runs). Row 12 is in the declared C2 surface.
   This is also why the declaration's separability sentence includes `tools/check-owed-statements-r29.py`.
7. [obs] Row 9's bash child is the only place where `BASH_ENV` and `ENV` would actually execute. The census (`tools/tsukuroi-census.sh`) only inherits `git_env()`, so C2 needs no census edit. That keeps C2 off C1's surface [inf].
8. [obs] Dependence on `tools/_revision.py` (sha256 06b71e8cb4aa541a25c95301106dc4d3ad9566cf18ec834f226ec0708db58cbf):
   - **Direct importers among the 11 targets:** rows 2, 3, 4, 5 and 6. Row 8 depends on it indirectly: it copies `tools/_*.py` next to the counter it runs (:77-79). Row 2's selftest copies it as well (:496-497).
   - **Who runs the `clean_env` body:** every one of those paths replaces `_revision.clean_env` before any git starts. Rows 2, 3 and 4 do it with a try/finally monkeypatch around each bind; rows 5 and 6 assign it at import. So no target child runs the body at :62-67 (code at the cited lines) [inf, strong]. C2 needs no edit to `_revision.py`.
   - **Effect of an edit:** an edit would trip `tools/check-pause-gate.py:244-248` (`GATE-BINDER-BYTES`, CANNOT_EVALUATE, return 2) and `tools/report-red-causes.py:202-204` (`RuntimeError('revision binder differs from the claim-base bytes')`). Both hash the working-tree file `ROOT/tools/_revision.py`.

   - Its dependency is behavioural: `from _revision import E_GIT, RevisionError, bind, clean_env` (:18), and it uses the unpatched `clean_env()` for its git children at :264, :459 and :933.
   - So editing `_revision.clean_env` would silently change that gate's child environment, but would not fail a digest check there.
