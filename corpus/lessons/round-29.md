## What the sources settle (C1, O01 to O04)

The v7.2 kernel has no band that is scanned or chosen first. `oom_badness()` gives every eligible task one number, resident plus swapped plus page-table pages, plus `oom_score_adj` times `totalpages / 1000` (S149 lines 228-234; S148 line 1777: the value "is added to the badness score"), and `select_bad_process()` keeps the single highest number over one pass (S149 lines 359-375; ties go to the later task). The adjustment is an offset: on the event host one adj unit was 16,909 pages, so +200 adds about 12.9 GiB of score-equivalent memory. The only no-scan path is `vm.oom_kill_allocating_task` (S150 lines 810-817; default 0, host 0 now, unknown at the events), plus the `task_will_free_mem(current)` and `oom_task_origin` shortcuts in S149. Event A's conclusion survives: its +200 victim won on footprint (17,460,384 points against 5,091,048 for the top +300 helper), not on its class. O03 is `qualified`, not corrected: "prefers the higher-scored tasks" is the rule, "first" and "larger-RSS" are not (RevOomMechanism, ScribeMarkersOom). `SKILL.md` gains the section "Kernel OOM victim selection — round 29", which also qualifies row F7 (`SKILL.md:1094`): the +100 manager beats a +200 task only with about 6.45 GiB more memory, so F7 holds as a magnitude condition, not as a class order (ScribeSkillOomRow, RevF7Quant).
