## Reading the rows

All anchors below are relative to `.ufo/waves/round-76/before/src/`, not installed Arch source lines.

- **JD1 — storage selection:** `journald.conf.xml:75-100`. `volatile` writes below `/run/log/journal`; `persistent` prefers `/var/log/journal`, creating it if needed, but falls back to runtime storage during early boot or when disk is unwritable. `auto` selects between these behaviors by directory existence. `none` drops stored data but does not disable forwarding. Initial volatile logging switches under the stated conditions through `journalctl --flush`/SIGUSR1, normally via `systemd-journal-flush.service`. The default namespace's compiled default must not be inferred from the `auto` rule.
- **JD2 — two constraints:** `journald.conf.xml:252-298`. System limits govern persistent storage and Runtime limits volatile storage. MaxUse limits journal consumption; KeepFree reserves filesystem space for other uses. The 10%/15%, each capped at 4G, are defaults, not overrides of an explicit MaxUse. The smaller permitted journal allowance wins, subject to the startup floor described next.
- **JD3 — actual arithmetic:** `journald-manager.c:143-173`, `cache_space_refresh()`: `avail = LESS_BY(vfs_avail, metrics->keep_free)` is saturated subtraction, not `min(free, keep_free)`. The limit is `CLAMP(vfs_used + avail, min_use, max_use)` and available growth is `LESS_BY(limit, vfs_used)`. `manager_do_vacuum()` at `journald-manager.c:796-814` passes that space limit plus the file-count and retention limits to `journal_directory_vacuum()`.
- **JD4 — startup floor:** `journald-manager.c:176-186`, `patch_min_use()`, sets `min_use = MAX(min_use, current_usage)` at startup/first opening; the source comment scopes reset to a journald restart. `journald.conf.xml:283-298` explains that another consumer filling the filesystem stops journal growth rather than shrinking the existing footprint to recover KeepFree. This does not promise that no old archived files can ever be removed: other retention constraints still exist.
- **JD5 — rotation granularity:** `journald.conf.xml:300-309`. The default per-file limit is `min(MaxUse/8, 128M)`; “usually seven” is an explanation, not a guaranteed retained-file count. The separate compact-mode ceiling is 4G, not the default file size. Size enforcement happens synchronously on file extension, without requiring a timed rotation step.
- **JD6 — count is not total inventory:** `journald.conf.xml:311-318`. The default is 100, but vacuum removes archived files, leaving active files; the post-vacuum total may exceed the configured number.
- **JD7 — compiled, not measured defaults:** `journald-config.c:24-27` defines the four constants. `journal_config_set_defaults()` at `journald-config.c:39-52` assigns the rate-limit pair; `manager_merge_configs()` at `journald-config.c:106-142` supplies sync and max-file-time fallback values. Thus the draft's attribution of all four assignments to `journal_config_set_defaults()` was too broad. These are defaults, not proof of effective per-service rate limits or live sync timing.
- **JD8 — vacuum surface:** `journalctl.xml:941-985`. Disk usage includes active and archived files, whereas vacuum-size/time/files act on archives. Time removes archives older than its duration; files limits archive count without deleting active files. The three constraints can combine; zero disables the corresponding constraint. With `--rotate`, active files are archived before the requested vacuum. This note documents the operation without executing it.

## Effective limits on this host

The frozen read-only receipt `.ufo/waves/round-76/before/host.txt` records systemd `262.1-1`, both journal directories, and the merged configuration. Its explicit `SystemMaxUse=256M` comes from `/etc/systemd/journald.conf.d/size.conf`; `RuntimeMaxUse=64M` is a separate volatile-storage constraint. Commented settings in the main file are not explicit overrides.

For the persistent-storage configuration calculation, the recorded filesystem has about 764 GB available, well above the default capped KeepFree of 4 GiB. The remaining allowance plus journal usage is therefore larger than 256 MiB, leaving MaxUse as the binding upper limit: `effective_limit=256M`. With no explicit per-file override shown, one eighth of 256 MiB is below the 128 MiB cap: `SystemMaxFileSize=32M`. These are derived configuration limits under the pinned mechanism, not a direct read of the running manager's cached state or its startup min_use.

`journalctl --disk-usage` observed `148.6M` across archived and active journals. The separate inventory reports 13 files and `sum_bytes=209715200`; apparent file lengths are not interchangeable with allocated-block disk usage. Neither the inventory nor the largest-file list establishes that every file has reached the configured default limit.
